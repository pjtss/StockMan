# 지속 개선 검토 운영

## 검토 주기

| 주기 | 확인 내용 | 결과 |
|---|---|---|
| 배포 직후 | smoke test, 핵심 API, migration, 오류 로그 | 즉시 회귀 과제 등록 |
| 매일 | 5xx·timeout·rate limit·데이터 지연 | 반복/급증 항목 우선 등록 |
| 매주 | 개선 백로그, 성능 추이, 사용자 동작 실패 | 우선순위 재조정 |
| 매월 | 오래된 문서·규칙·테스트·지표의 유효성 | 폐기·통합·자동화 결정 |

## 우선순위

각 과제는 영향도와 발생 가능성을 각각 1~5로 평가하고, `위험도 = 영향도 × 가능성`으로 정렬한다. 보안·데이터 손상·잘못된 투자 데이터는 점수와 관계없이 최우선이다.

## 성과 판정

개선 전 기준값과 배포 후 비교값을 함께 기록한다. 성공 기준은 과제별로 명시하며, 예시는 다음과 같다.

- API: p95 응답시간, 5xx 비율, 비JSON 응답률
- KIS: 호출량, rate limit 횟수, 빈 응답률, 최신 데이터 지연
- DB: 쿼리 p95, timeout, connection error
- UI: 핵심 동작 성공 여부, 클라이언트 오류, 모바일 overflow

측정값이 없으면 `검증되지 않음`으로 처리하고 완료 상태로 올리지 않는다.

## 검토 기록 템플릿

```text
검토일:
대상 기간:
확인한 지표:
개선 전 기준값:
현재값:
판정: IMPROVED | UNCHANGED | REGRESSED | UNMEASURED
새로 발견한 위험:
다음 과제 ID:
문서·테스트·자동 게이트 갱신 여부:
```

## 미해결 위험 관리

미해결 위험은 숨기거나 완료 처리하지 않고 담당 모듈, 영향, 완화책, 재검토일을 기록한다. 같은 위험이 재검토일에 남아 있으면 우선순위를 다시 계산하고, 자동 감지가 불가능하면 먼저 관찰 지표를 만든다.

현재 문서는 운영 기준과 템플릿을 제공한다. 실제 검토 결과는 `DEVELOPMENT_LOG.md`에 날짜별로 남겨 다음 작업의 입력으로 사용한다.
