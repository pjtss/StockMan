# 지속 개선 운영 기준

상태가 `완료`로 끝나는 기능은 없다. 배포된 기능은 항상 운영 관찰 대상이며, 관찰 결과는 개선 백로그의 입력이 된다.

## 개선 루프

```text
운영 지표 수집 → 이상·반복 패턴 탐지 → 개선 과제 등록 → 영향·우선순위 평가
→ 설계 변경 → 구현·회귀 테스트 → 배포 게이트 → 운영 결과 비교 → 과제 갱신
```

## 기능별 최소 관찰 지표

| 영역 | 필수 지표 | 개선 신호 |
|---|---|---|
| API | 요청 수, 성공률, p50/p95 응답시간, 비JSON·5xx 비율 | 오류율·p95 증가, 동일 오류 반복 |
| 외부 API | 호출량, rate limit, 재시도, 빈 응답, 최신 수집시각 | 제한 초과, 빈 응답 증가, 데이터 지연 |
| DB | 쿼리시간, timeout, 연결 오류, migration 상태 | p95 증가, 반복 timeout, 버전 불일치 |
| UI | 핵심 동작 성공률, 클라이언트 오류, 모바일 overflow | 클릭 실패, 콘솔 오류, 화면 잘림 |
| 배포 | 검증 실패 단계, 배포 성공률, smoke test 결과 | 같은 단계의 반복 실패 |

## 개선 과제 템플릿

```text
ID:
발견일:
영역/API:
문제와 사용자 영향:
측정 근거:
근본 원인 가설:
우선순위와 이유:
수용 기준:
수정할 코드·문서·테스트:
재발 자동 감지 방법:
배포 후 비교할 지표:
상태: BACKLOG | DESIGNED | IMPLEMENTED | VERIFIED | OBSERVING | IMPROVING
남은 위험:
```

## 운영 회고 규칙

- 배포마다 실패 단계, 실제 응답, 핵심 지표를 기록한다.
- 같은 오류가 두 번 발생하면 회고 대상, 세 번째 발생 전 자동 게이트 또는 회귀 테스트를 추가한다.
- 개선 과제는 수치 또는 재현 절차 없이 완료 처리하지 않는다.
- 배포 후 예상치와 실제치를 비교하고, 차이가 있으면 과제의 가설과 문서를 갱신한다.
- 오래된 문서는 현재 코드·API·DB 상태와 대조해 폐기·통합·갱신한다.

## 현재 백로그

개선 과제는 작업 시 이 문서의 템플릿으로 등록하고, 완료 시에도 `OBSERVING` 상태로 남겨 운영 결과를 확인한다. 백로그가 비어 있는 것은 개선할 문제가 없다는 뜻이 아니라 다음 관찰 주기를 기다리는 상태다.

검증 파이프라인의 단계별 병목은 `npm run measure:verify`로 측정한다. 결과 JSON의 `stages[].durationMs`를 이전 실행과 비교해 성능 개선 근거로 사용한다.

연속 비교가 필요하면 `npm run measure:verify -- --out reports/verify-latest.json`처럼 결과 파일을 지정한다. 결과에는 Node 버전·OS·아키텍처·CPU 코어 수와 측정 시점·Git HEAD·작업 트리 변경 여부만 기록하며, 민감정보·명령 인자·환경변수·파일 내용은 기록하지 않는다. 비교 시 Git HEAD가 다르면 `CODE_MISMATCH`와 낮은 신뢰도로 표시한다.

기준 결과와 비교하려면 `npm run compare:verify -- reports/verify-baseline.json reports/verify-latest.json 0.2`를 사용한다. 기본 권장 임계치는 20%이며, 초과한 단계는 `REGRESSED`로 판정하고 명령을 실패시킨다.

비교 결과는 실행 환경이 다르면 `ENVIRONMENT_MISMATCH`와 `confidence: LOW`, 재측정 권고를 별도로 표시한다. 환경 차이는 성능 회귀와 분리해 판단하며, 원인 확인 없이 회귀로 확정하지 않는다.

기준 결과의 단계가 현재 결과에서 사라지면 `missingStages`로 표시하고 비교 명령을 실패시킨다. 새 단계는 `newStages`로 표시하고 `scopeStatus: REVIEW_REQUIRED`로 판정해 기준값 승인 전 비교 명령을 실패시킨다. 단계 범위가 동일할 때만 `scopeStatus: APPROVED`가 된다.

승인된 검증 단계는 `config/verify-scope.json`에서 관리한다. manifest에 없는 현재 단계는 `unapprovedStages`로 표시하고 비교를 실패시킨다.

manifest에는 변경 사유(`changeReason`), 승인 주체(`approvedBy`), 승인일(`approvedAt`)을 함께 기록한다. 세 메타데이터가 유효하지 않으면 비교 자체를 시작하지 않는다.

manifest를 변경할 때는 `npm run audit:verify-scope`로 변경 diff에도 세 메타데이터가 포함됐는지 확인한다.

## 변경 이력 자동 게이트

모든 작업은 `DEVELOPMENT_LOG.md`의 최신 날짜 항목에 `### 목표`, `### 반영`, `### 검증`, `### 다음 개선`, `### 개선 과제`와 `커밋·푸시·배포` 상태를 기록한다. 개선 과제에는 `CI-YYYY-MM-DD-NNN` 형식의 고유 ID, 허용된 성과 판정, 판정의 `근거:`를 남긴다. `### 검증`에는 실제 실행 명령 또는 측정값을, `### 다음 개선`에는 구체적인 목록을 포함한다. 배포 상태는 `미실행`, `완료`, `실패`, `차단` 중 하나로 기록하고, 완료 시 커밋 식별자를 남긴다. `npm run docs:check`가 이 계약과 값 형식, 전체 ID 중복 여부를 자동 검사하므로, 다음 개선이나 근거 있는 성과 판정 없이 기록만 누적되는 작업은 배포 전 게이트에서 차단한다.
