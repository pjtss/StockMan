# 기획·개발·테스트·배포·개선 생명주기

## 원칙

모든 변경은 기획의 수용 기준에서 시작해 코드·테스트·배포 검증·운영 관찰·개선 반영으로 닫힌다. 문서는 과거를 저장하는 곳이 아니라 다음 작업의 입력과 자동 검증 기준을 갱신하는 운영 도구다. 테스트나 빌드가 통과했다는 사실만으로 운영 완료로 표시하지 않는다.

## 단계별 산출물과 게이트

| 단계 | 필수 산출물 | 완료 게이트 |
|---|---|---|
| 기획 | 요구사항, 범위, 수용 기준, 영향 영역 | 사용자 시나리오와 비범위가 문서에 명시됨 |
| 설계 | 모듈 경계, API/DB 계약, 실패·성능 계획 | 기존 아키텍처·SRP·공식 API 문서와 충돌 없음 |
| 개발 | 구현 코드, 관련 문서, 회귀 테스트 | 변경 책임이 단일 모듈 경계를 지킴 |
| 로컬 검증 | 테스트·타입검사·문서검사·빌드·실행 결과 | `npm run deploy:verify` 전체 통과 |
| 배포 | 커밋, 브랜치, CI 실행 결과 | CI의 검증·standalone·활성화 단계 성공 |
| 운영 확인 | health, 핵심 API, DB/Flyway, 로그 | 실제 응답과 적용 버전 확인 |
| 개선 | 장애 원인, 영향, 수정, 재발 방지, 다음 검증 항목 | `docs/ERROR_HANDLING.md`·관련 설계·자동 게이트 갱신 |

## 변경 기록 규칙

- 기능·오류·성능 변경은 `Development.md` 또는 `DEVELOPMENT_LOG.md`에 날짜, 영향, 검증 결과와 다음 개선 작업을 기록한다.
- DB 변경은 기존 migration을 수정하지 않고 새 버전으로 추가한다.
- CI에서 발견된 실패는 원인을 해결하기 전 배포 성공으로 보고하지 않는다.
- 같은 실패가 반복되면 체크리스트·자동 검사·문서 중 하나를 반드시 강화하고, 강화된 검사가 실제 CI에서 실행되는지 확인한다.
- 커밋에는 변경 범위를 명확히 남기고, 관련 없는 로컬 파일은 포함하지 않는다.

## 반복 오류 방지 루프

`실패 감지 → 원인 분류 → 최소 수정 → 회귀 테스트 → 자동 게이트 보강 → 운영 확인 → 문서 기록 → 다음 작업에 규칙 반영` 순서를 지킨다. 각 기록에는 반드시 `문제`, `근본 원인`, `영향`, `수정`, `검증`, `재발 시 자동 감지 방법`, `남은 위험`을 남긴다. 동일 오류가 다시 발생하면 기존 수정이 실제 배포 산출물에 포함됐는지와 CI가 그 조건을 검사하는지부터 확인한다.

## 문서의 유효성 검토

- 배포 전에는 이번 변경과 관련된 문서의 완료 조건을 다시 읽고, 현재 코드·테스트·CI 명령과 일치하는지 확인한다.
- 배포 후에는 운영 결과를 문서의 가설과 비교한다. 예상과 실제가 다르면 문서를 수정하고 회귀 테스트 또는 자동 게이트를 추가한다.
- 분기 없이 반복되는 기록은 요약하지 말고, 공통 원인을 하나의 규칙·검사·모듈 개선으로 승격한다.
- 완료 문서에는 “다음에 무엇을 자동으로 검증할지”가 있어야 하며, 없으면 단순 로그로 간주한다.
