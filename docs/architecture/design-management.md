# 설계 문서 관리 기준

## 목적

기능 제안이 늘어날 때 설계의 현재 상태, 결정 근거, 미확인 전제, 후속 개선을 잃지 않도록 공통 생명주기와 문서 책임을 정의한다. 새 기능의 요구사항과 상태를 알리는 기준점은 기능별 설계서이며, 이 문서는 설계 문서의 작성·갱신 방법만 관리한다.

## 문서 위치와 역할

| 문서 | 책임 |
|---|---|
| `docs/architecture/design-management.md` | 설계 생명주기·갱신 규칙·검토 기준 |
| `docs/architecture/design-template.md` | 새 설계서 또는 큰 개정 때 복사할 최소 형식 |
| `docs/architecture/<기능>-design.md` | 해당 기능의 목적, 요구사항, 결정, 구조, 상태, 미해결점 |
| `docs/operations/<기능>-runbook.md` | 이미 구현된 기능의 운영·복구·일정 절차 |
| `DEVELOPMENT_LOG.md` | 날짜별 조사·문서화·코드 변경·검증·전달 기록 |
| `docs/ERROR_HANDLING.md` | 실제 오류의 근본 원인, 해결, 재발 감지 |

설계서는 아키텍처 영역에 모으고 인덱스에 링크한다. 운영 절차와 매일의 변경 내역을 설계서에 누적하지 않는다. 같은 정책을 여러 문서에 복사하지 말고 권위 문서 하나를 정해 링크한다. 설계 전용 README나 세부사항 없는 목차 문서는 만들지 않는다.

## 상태와 변경 흐름

상태는 다음 중 하나를 문서 상단에 표시한다.

- `제안`: 구조 또는 요구사항이 검토 중이며 구현 승인과 동일하지 않다.
- `검토 중`: 코드·운영·공식 근거와 대조하고 있다.
- `승인`: 명시된 요구사항과 결정이 합의됐으나 구현 여부는 별도다.
- `구현 중`: 승인된 범위의 코드 작업이 진행 중이다.
- `운영`: 구현 및 운영 경로가 검증되어 현재 기준으로 사용한다.
- `보류`: 의존성, 근거, 결정이 없어 진행하지 않는다. 사유와 재개 조건을 적는다.
- `폐기`: 대체 문서 또는 기능을 링크하고 폐기 이유와 날짜를 남긴다.

갱신할 때는 먼저 최신 요구사항과 현재 구현·운영 문서를 대조하고, 바뀐 항목만 설계서에 반영한다. 알고리즘·보안·데이터 계약에 영향을 주는 값은 기존 값을 조용히 덮어쓰지 말고 결정 기록에 날짜, 근거, 영향, 대안을 적는다. 확정되지 않은 사항은 본문에 단정하지 않고 `미결`로 유지한다. 구현 뒤에는 설계의 상태와 실제 경로·검증 증거를 갱신한다.

## 검토 체크리스트

1. 목적, 범위, 비목표, 사용자 결과가 구분되어 있는가?
2. 현재 코드와 프로젝트의 `AGENTS.md` 불변식에 맞는가? 충돌은 임의로 해결하지 않고 노출했는가?
3. 데이터 출처·분류 권위·시각·최신성·누락·부분 실패 처리가 명시됐는가?
4. API 접근 분류, 입력·출력 계약, 오류, 부수효과가 분리되어 있는가?
5. 계산 규칙이 재현 가능하고 임계값·경계 사례·버전이 추적되는가?
6. 스케줄러, 저장소, 동시성, 원자성, 복구 및 모니터링의 전제가 확인됐는가?
7. 보안·성능·배포 제약, 남은 위험, 재발 자동 감지가 적혀 있는가?
8. 공식 문서나 코드 근거에 직접 연결되어 있는가? 제안과 검증된 사실이 구분되는가?
9. 인덱스와 개발 로그가 갱신되고 문서 링크·인코딩이 유효한가?

## 변경 이력과 완료 기준

모든 조사·문서 변경은 `DEVELOPMENT_LOG.md`에 목적, 대상, 반영 내용, 검증과 한계, 다음 개선, 개선 과제 ID와 성과 판정, 커밋·푸시·배포 여부를 기록한다. 오류·성능·기능 변경은 `docs/ERROR_HANDLING.md`와 테스트·자동 검사 연결 필요성도 평가한다. 문서 작성만으로 구현·승인·배포 완료를 뜻하지 않는다.

새 설계의 기본 성과 판정은 `UNMEASURED`이며, 실제 개선이 검증되기 전 `IMPROVED`로 표시하지 않는다. 기존 설계에서 충돌·누락을 발견하면 구체적 근거와 해결 경로를 기록하고, 사용자 요청 범위를 벗어난 코드는 변경하지 않는다.
