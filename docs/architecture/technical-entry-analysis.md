# 기술적 상승 진입 후보 분석 설계

상태: 운영 기준 정리 및 단계적 적용

## 1. 목적

현재 프로젝트의 KIS 원본 데이터와 PostgreSQL 캔들 캐시를 사용해, 가격 추세·모멘텀·추세 강도·거래량·자금 흐름·과매수 위험을 종합한 상승 진입 후보를 선별한다.

분석 결과는 종목 정보 표와 쉼표 구분 티커 목록으로 제공한다.

## 2. 기존 구조와의 관계

새로운 KIS 조회 체계를 만들지 않고 다음 기존 모듈을 재사용한다.

```text
활성 종목 유니버스
→ 종목별 최신성 검증
→ 부족한 봉만 KIS 조회
→ 캔들 DB upsert
→ 지표 계산
→ 후보 필터·점수화
→ 표준 응답 생성
```

- 국내 유니버스: `kr_common_stock_universe`
- 해외 유니버스: `us_common_stock_universe`
- 캔들 캐시: `*_instrument_universe_candles`
- KIS 요청: `lib/kis-*`
- 캔들 저장: `lib/*daily-price-cache*`
- 실행 중복 제어: PostgreSQL advisory lock
- 실패 재처리: candle cache retry queue

## 3. 분석 대상 필터

### 국내

- `enabled = true`
- `instrument_type = 'COMMON_STOCK'`
- 거래정지·관리·상장폐지 상태 제외
- 최신 일봉 거래량이 0보다 큰 종목
- 시가총액 정보가 있고 요청 하한 이상인 종목

거래량이 0인 최신 일봉이 저장되면 해당 보통주는 비활성화한다. 이후 양수 거래량의 최신 일봉이 저장되고 공식 제외 상태가 아니면 다시 활성화한다.

국내 종목의 기본 시가총액 하한은 300억 원이며, 사용자 요청이 더 높은 하한을 지정하면 요청값을 적용한다.

### 해외

- `enabled = true`
- `COMMON_STOCK`
- ETF·ETN·워런트·파생·레버리지·인버스·DR 제외
- 거래소별 최신 거래일과 휴장일 반영

## 4. 데이터 최신성 및 완결성

전체 테이블의 전역 `MAX(fetched_at)`만으로 최신 여부를 판정하지 않는다. 반드시 종목별로 판정한다.

```text
종목별 최신 일봉 거래일
종목별 최신 주봉 기간 종료일
종목별 최신 월봉 기간 종료일
각 봉의 fetched_at
진행 중 봉 여부
```

분석 시작 시 기준 시각을 고정한다.

```text
analysisStartedAt
dataCutoffAt
dailyLatestDate
weeklyLatestDate
monthlyLatestDate
```

종목 데이터 상태:

| 상태 | 기준 |
|---|---|
| `COMPLETE` | 필수 봉과 지표 계산 가능 |
| `PARTIAL` | 일부 지표만 계산 가능 |
| `STALE` | 최신 거래일 기준 미달 |
| `INVALID` | 거래량 0, 봉 누락, 비정상 OHLC |
| `FAILED` | KIS 또는 DB 오류 |

최종 후보는 `COMPLETE`만 허용한다.

## 5. 지표 정의

일반 이동평균은 프로젝트 규칙에 따라 EMA를 사용한다.

- EMA 9 / EMA 20
- MACD 12 / 26 / 9
- OBV Signal: EMA 20
- ADL Signal: EMA 20
- Bollinger Bands: 20 / 2
- DMI 및 ADX 14
- MFI 14
- RSI 14
- Stochastic 14 / 3 / 3
- 거래량 SMA 20
- RVOL
- 최근 가격 고점·저점
- 지지·저항

SMA 20은 일반 추세선으로 사용하지 않고 볼린저밴드 중단선과 거래량 평균 등 해당 지표 정의 안에서만 사용한다.

## 6. 골든크로스 판정

### 실제 교차

```text
직전 fast <= 직전 slow
현재 fast > 현재 slow
```

적용 대상:

- EMA 9 / EMA 20
- MACD / Signal
- +DI / -DI
- OBV / OBV Signal
- ADL / ADL Signal
- Stochastic %K / %D

### 접근 중

최소 3개 봉에서 간격이 연속 축소될 때 접근 중으로 판정한다.

```text
abs(현재 간격) < abs(직전 간격)
abs(직전 간격) < abs(2봉 전 간격)
```

신호 수명:

| 상태 | 기준 |
|---|---|
| `CROSSED_TODAY` | 현재 봉에서 교차 |
| `CROSSED_RECENT` | 1~3봉 전 교차 |
| `APPROACHING` | 교차 전 간격 축소 |
| `RECENT` | 4~10봉 전 교차 |
| `EXPIRED` | 10봉 초과 |

## 7. 점수 체계

골든크로스 개수를 단순 합산하지 않고 영역별로 점수화한다.

| 영역 | 배점 |
|---|---:|
| 가격 추세·EMA | 20 |
| MACD·모멘텀 | 15 |
| DMI·ADX | 20 |
| OBV·ADL 자금 흐름 | 20 |
| 거래량·RVOL | 15 |
| 과매수 위험 | 10 |
| 합계 | 100 |

같은 가격 기반 지표의 중복 신호는 영역별 최대 점수를 초과하지 않는다.

추가 원칙:

- 최근 실제 교차에 높은 가점
- 교차 직전의 간격 축소에 중간 가점
- 오래된 교차는 감점
- 가격 상승·거래량 증가·OBV·ADL 동시 상승은 추가 가점
- 점수 60점 미만은 최종 후보에서 제외
- 손익비 1.5 미만은 최종 후보에서 제외

## 8. 제외 및 경고 조건

- MFI >= 80
- RSI >= 70
- Stochastic >= 80
- RVOL < 0.7
- ADX < 20이면서 하락
- 가격 상승 중 OBV·ADL 동시 하락
- 최신 일봉 거래량 0
- 최신 완료봉 없음
- 필수 이력 부족
- 최근 고점 대비 과도한 급등
- 지지·저항 또는 손익비 계산 불가

## 9. 진입 가격 계산

임의 가격을 사용하지 않는다.

- 현재가: 최신 완료 일봉 종가
- 추천 매수가: 현재가 또는 최근 지지선 부근
- 1차 목표가: 최근 저항선
- 2차 목표가: 최근 고점 또는 ATR 기반 목표가
- 손절가: 최근 스윙 저점 또는 ATR 기반
- 손익비: `(목표가 - 매수가) / (매수가 - 손절가)`

계산이 불가능하면 가격을 제시하지 않고 후보에서 제외한다.

## 10. 응답 형식

종목 정보는 표로 제공한다.

| 순위 | 종목코드 | 종목명 | 시장 | 종합점수 | 실제 GC | GC 접근 | MACD | DMI/ADX | OBV/ADL | 거래량/RVOL | MFI/RSI | 판단 |
|---:|---|---|---|---:|---|---|---|---|---|---|---|---|

모든 응답에는 다음 메타데이터를 포함한다.

- 기준일
- 데이터 기준 시각
- 종목별 최신 일봉·주봉·월봉 거래일
- 각 봉의 DB 갱신 시각
- 종목명·종목코드
- 데이터 출처
- 완료봉 여부

표 아래에는 다음 형식으로 티커를 제공한다.

```text
티커:
종목코드,종목코드,종목코드
```

조건을 만족하는 종목이 없으면 `현재 진입 적합 종목 없음`으로 응답한다.

## 11. 성능 및 운영 원칙

- KIS 조회·파싱·DB upsert·지표 계산·후보 선별 책임을 분리한다.
- 종목별 stale 데이터만 KIS에서 조회한다.
- DB upsert는 배치 단위로 처리한다.
- KIS 계정 호출 제한은 공통 throttle로 준수한다.
- 작업 중복은 메모리 캐시와 PostgreSQL advisory lock으로 차단한다.
- 장시간 작업은 checkpoint와 retry queue를 사용한다.
- 동일 데이터·동일 정책의 반복 분석은 결과 캐시를 재사용한다.
- 지표 계산 캐시 키에는 `indicatorVersion`과 `policyHash`를 포함한다.

## 12. 구현 단계

- 해외 일·주·월봉 timeframe별 적재 레인

- 국내·해외 기초정보 batch upsert
- 1분봉 행 단위 INSERT 제거

## 13. 검증 기준

기능 변경 시 반드시 로컬 DB를 먼저 사용한다.

```text
로컬 DB 연결 확인
→ 로컬 실제 데이터 테스트
→ 최신 거래일·거래량·활성 상태 검증
→ KIS 원본과 DB 적재 결과 대조
→ 타입검사
→ 관련 단위 테스트
→ 전체 테스트
```

로컬 DB 검증 없이 기능을 확정하지 않는다.

## 14. 추가 정밀화 규칙

### 14.1 분석 스냅샷

한 번의 분석에서는 서로 다른 시점의 데이터를 혼합하지 않는다. 분석 시작 시 `dataCutoffAt`을 고정하고, 모든 종목과 timeframe은 해당 시각 이전에 저장된 완료 봉만 사용한다.

```text
analysisId
dataCutoffAt
indicatorVersion
policyHash
```

분석 도중 새 캔들이 저장되어도 현재 분석 결과에는 반영하지 않는다. 다음 분석에서 새 스냅샷으로 반영한다.

### 14.2 거래일 캘린더

최신 거래일은 서버 시간이나 달력 날짜로 추정하지 않는다.

- 국내: KOSPI·KOSDAQ 거래일 기준
- 해외: 거래소별 거래일 기준
- 휴장일·조기 폐장일 반영
- 진행 중 봉과 완료 봉 구분

거래일 캘린더를 확인할 수 없으면 최신성 판정을 `UNKNOWN`으로 표시하고 후보에서 제외한다.

### 14.3 종목별 데이터 품질 점수

후보를 계산하기 전 데이터 품질을 먼저 평가한다.

| 항목 | 검증 |
|---|---|
| 날짜 | 중복·역순·미래 날짜 없음 |
| OHLC | 고가 >= 시가·종가, 저가 <= 시가·종가 |
| 거래량 | 음수 없음, 최신 완료 일봉은 양수 |
| 이력 | 지표별 최소 봉 수 충족 |
| 갱신 | 거래소 최신 거래일과 일치 |
| 출처 | KIS 또는 허용된 DB 원본 |

필수 검증 실패 시 지표 점수를 계산하지 않고 `INVALID` 또는 `STALE`로 종료한다.

### 14.4 최소 이력

지표별 워밍업 이력을 고정한다.

- EMA·MACD: 최소 60봉
- DMI·ADX: 최소 60봉
- Bollinger Bands: 최소 40봉
- OBV·ADL·MFI·RSI: 최소 40봉
- Stochastic: 최소 30봉
- 지지·저항: 최소 120봉 권장

필요 이력이 부족한 종목은 부분 점수로 보정하지 않고 최종 후보에서 제외한다.

### 14.5 점수와 신호의 독립성

점수는 지표 개수가 아니라 독립 영역의 확인 수를 평가한다.

```text
가격 추세 확인
모멘텀 확인
추세 강도 확인
자금 흐름 확인
거래 참여 확인
위험 조건 확인
```

동일 영역 내 지표가 여러 개 충족되어도 영역 배점을 초과하지 않는다. 가격 기반 지표만으로 전체 점수의 50% 이상을 획득할 수 없게 제한한다.

### 14.6 신호 충돌 처리

상승 신호와 위험 신호가 동시에 존재하면 단순 합산하지 않는다.

- OBV·ADL 동시 하락: 최종 점수 상한 59점
- 거래량 감소: 거래량 영역 0점
- ADX 하락: 추세 강도 영역 감점
- RSI·MFI·Stochastic 과매수: 추격 진입 제외
- 최신 봉 거래량 0: `INVALID`

### 14.7 가격 전략 산출 실패

다음 경우에는 후보는 표시하되 가격 전략은 `산출 불가`로 표시하거나 최종 진입 후보에서 제외한다.

- 지지선과 손절선이 현재가보다 높음
- 목표가가 현재가보다 낮음
- 손절 폭이 0 또는 비정상적으로 큼
- 손익비 1.5 미만
- 최근 급등으로 저항선까지 여유가 부족함

### 14.8 재현성

같은 `analysisId`와 동일한 데이터 스냅샷·정책이면 같은 결과가 나와야 한다.

응답에 다음을 포함한다.

```text
indicatorVersion
policyHash
dataCutoffAt
sourceSnapshot
```

정책 변경 없이 결과가 달라지면 데이터 변경, 거래일 변경, 계산 오류 중 하나로 분류해 기록한다.

## 15. 운영 및 실패 격리

분석 전체가 한 종목의 오류로 실패하지 않도록 종목 단위로 격리한다.

- KIS 오류: 해당 종목만 `FAILED`
- DB 조회 오류: 해당 작업을 실패 처리하고 retry
- 계산 오류: 해당 종목만 `INVALID`
- 전체 스냅샷 불일치: 분석 전체 중단

작업 결과에는 다음 통계를 남긴다.

```text
totalCount
completeCount
staleCount
invalidCount
failedCount
qualifiedCount
kisRequestCount
dbReadCount
dbUpsertCount
durationMs
```

## 16. API 응답 계약

분석 API는 화면용 결과와 기계용 메타데이터를 동일 응답에 포함한다.

```json
{
  "ok": true,
  "analysisId": "...",
  "checkedAt": "...",
  "dataCutoffAt": "...",
  "source": "KIS_DB_CACHE",
  "policy": {},
  "statistics": {},
  "timeframes": {},
  "results": [],
  "tickers": "AAA,BBB,CCC"
}
```

종목별 결과에는 반드시 `market`, `code`, `name`, 최신 거래일, 갱신 시각, 출처를 포함한다.

## 17. 테스트 추가 기준

로컬 DB 테스트는 정상 케이스만 확인하지 않는다.

- 최신 일봉 거래량 0 → 비활성화
- 거래량 0에서 양수 회복 → 재활성화
- 최신 거래일 이전 봉 → `STALE`
- 휴장일 → 정상 최신으로 판정
- 진행 중 봉 → 완료봉 분석에서 제외
- 골든크로스 실제 교차와 접근 중 구분
- 지표별 최소 이력 부족
- OBV·ADL 상승과 하락 충돌
- 중복 실행 advisory lock

## 19. v2 추가 개선안

### 19.1 데이터 계약과 계산 계약 분리

입력 데이터 규칙과 지표 계산 규칙을 분리해 관리한다.

```text
MarketDataContract
→ CandleValidationContract
→ IndicatorCalculationContract
→ SignalContract
→ RankingContract
→ ResponseContract
```

각 계약은 독립적으로 버전 관리한다.

```text
dataContractVersion
indicatorVersion
signalVersion
rankingVersion
responseVersion
```

계산식이 바뀌지 않은 상태에서 응답 표기만 변경된 경우에도 지표 결과와 구분할 수 있어야 한다.

### 19.2 원본·정규화·파생 데이터 구분

DB 데이터는 다음 세 계층으로 구분한다.

| 계층 | 내용 |
|---|---|
| Raw | KIS 원본 payload와 원본 거래일 |
| Normalized | 표준 OHLCV와 정규화된 날짜·수치 |
| Derived | EMA·MACD·ADX·OBV 등 계산 결과 |

파생 결과에 원본 봉을 다시 저장하지 않는다. 파생 결과는 원본 캔들 키와 계산 버전을 참조한다.

### 19.3 봉 확정성 정책

분석 요청마다 봉 확정성 정책을 명시한다.

```text
completedOnly: true
includeCurrentSession: false
```

기본값은 완료봉만 사용한다. 진행 중인 일봉·주봉·월봉은 별도 데이터로 표시하며 골든크로스와 진입 점수에 사용하지 않는다.

### 19.4 신호 강도와 진입 적합성 분리

종합점수와 진입 판단은 같은 값으로 처리하지 않는다.

```text
signalScore
→ 기술적 상승 신호의 강도

entryScore
→ 현재 가격에서 실제 진입할 수 있는 정도
```

예시:

- `signalScore` 높음 + `entryScore` 낮음: 상승 추세지만 추격 위험
- `signalScore` 중간 + `entryScore` 높음: 초기 전환이나 확인 부족
- 두 점수 모두 높음: 최종 우선 후보

### 19.5 신호 상태 머신

신호를 단순 boolean으로 저장하지 않는다.

```text
BEFORE
→ APPROACHING
→ CROSSED
→ CONFIRMED
→ EXTENDED
→ FAILED
```

상태 전환에는 다음 정보를 저장한다.

- 전환 시각
- 전환 거래일
- 전환 봉 수
- 직전 간격
- 현재 간격
- 확인 조건
- 실패 조건

### 19.6 리스크 플래그 우선 처리

리스크 플래그는 점수 계산 후 부가 표시하지 않고, 후보 선별 전에 처리한다.

```text
데이터 무효
→ 즉시 제외

거래량 0
→ 활성 유니버스 제외

과매수·추격 위험
→ 진입 후보 제외 또는 경고

손익비 부족
→ 가격 전략 제외
```

이를 통해 높은 기술 점수가 위험 조건을 상쇄하지 못하게 한다.

### 19.7 결과 품질 등급

후보마다 기술적 적합성과 데이터 신뢰도를 별도로 표시한다.

| 등급 | 기준 |
|---|---|
| A | 최신 완료봉·모든 지표·가격 전략 완성 |
| B | 지표는 완성됐으나 가격 전략 일부 제한 |
| C | 신호는 있으나 보조 확인 부족 |
| D | stale·partial·계산 제한 |

최종 추천은 A 또는 B 등급만 허용한다.

### 19.8 후보 중복과 상관성 제한

같은 업종·같은 테마 종목이 결과를 과도하게 점유하지 않도록 선택 단계에서 제한한다.

- 동일 종목 중복 결과 제거
- 동일 종목의 timeframe별 신호 통합
- 업종·테마 집중도 표시
- 동일 신호 원인만 가진 후보의 과다 노출 방지

단, 업종·테마 정보가 공식적으로 확인되지 않으면 임의 분류하지 않고 `UNKNOWN`으로 표시한다.

### 19.9 결과 만료와 재검증

결과에는 만료 조건을 포함한다.

```text
resultExpiresAt
invalidateOnNewCandle
invalidateOnUniverseChange
invalidateOnPolicyChange
```

다음 상황에서는 기존 결과를 재사용하지 않는다.

- 새 완료봉 저장
- 종목 활성 상태 변경
- 시가총액 필터 변경
- 지표 정책 변경
- 계산 버전 변경

### 19.10 운영 승인 체크리스트

기능 확정 전 다음을 모두 확인한다.

- 로컬 DB에서 실제 데이터로 검증
- KIS 원본과 정규화 값 대조
- 최신 거래일과 `fetched_at` 확인
- 거래량 0 종목 제외 확인
- 활성·비활성 전환 확인
- 진행 중 봉 제외 확인
- 실제 교차와 접근 중 구분 확인
- 지표 최소 이력 검증
- stale·partial 종목 제외 확인
- 가격 전략 손익비 검증
- 동일 스냅샷 재실행 결과 비교
- 관련 테스트와 전체 타입검사 통과

## 20. 금지 사항

다음 구현은 허용하지 않는다.

- 오래된 봉을 최신 봉으로 간주
- 거래량 0 종목을 활성 후보로 출력
- 실패한 KIS 응답을 정상 데이터로 저장
- 진행 중 봉을 완료봉으로 표시
- SMA를 일반 이동평균선으로 사용
- 골든크로스 개수만으로 순위 결정
- 점수만으로 목표가·손절가를 임의 생성
- 데이터가 부족한 종목을 추정값으로 보정해 추천
- 사용자 요청 없이 유니버스·필터·정책을 임의 변경

## 21. 계산 입력·출력 계약

모든 지표 계산 함수는 동일한 입력 정렬 규칙을 사용한다.

```text
입력: 오래된 봉 → 최신 봉 순서
날짜: YYYYMMDD 또는 ISO 날짜로 정규화
가격·거래량: 유한한 양수만 사용
출력: 최신 봉 기준 값과 직전 봉 기준 값 함께 반환
```

지표 계산 함수는 원본 배열을 변경하지 않는다. 입력 봉이 부족하면 0이나 임의의 보정값을 반환하지 않고 `ready = false`를 반환한다.

표준 출력 형태:

```json
{
  "value": null,
  "previousValue": null,
  "ready": false,
  "signal": "INSUFFICIENT_HISTORY",
  "signalDate": null,
  "barsSinceSignal": null
}
```

## 22. 지표별 판정 계약

### 추세

```text
EMA9 > EMA20: 상승 추세
EMA9 교차 발생: 실제 상승 전환
EMA9와 EMA20 간격 축소: 접근 중
```

### 모멘텀

```text
MACD > Signal: 양의 모멘텀
MACD Histogram 증가: 모멘텀 강화
```

### 추세 강도

```text
+DI > -DI AND ADX >= 20: 유효 상승 추세
+DI > -DI AND ADX < 20: 약한 상승 방향
ADX 현재값 > ADX 직전값: 추세 강화
```

### 자금 흐름

```text
OBV > OBV Signal AND OBV 최신값 > 직전값: 매집 확인
ADL > ADL Signal AND ADL 최신값 > 직전값: 자금 유입 확인
```

OBV와 ADL 중 하나만 상승하는 경우에는 `부분 확인`으로 표시한다.

### 거래량

```text
RVOL = 최신 거래량 / 거래량 EMA 또는 정책상 평균 거래량
RVOL >= 1.2: 증가
0.7 <= RVOL < 1.2: 보통
RVOL < 0.7: 부족
```

거래량 평균의 종류는 정책에 저장하며, 일반 이동평균선 정책과 혼동하지 않는다.

## 23. 결측·이상치 처리

결측값은 지표별로 독립 처리한다.

- 한 지표 결측이 전체 종목 실패로 전파되지 않음
- 핵심 영역 2개 이상 결측이면 최종 후보 제외
- OHLC 불변 또는 거래량 0은 데이터 품질 경고
- 음수 가격·거래량은 즉시 무효 처리
- 중복 거래일은 최신 `fetched_at` 레코드 하나만 선택
- 미래 거래일은 제외하고 오류 통계에 기록

결측을 0으로 치환해 골든크로스나 점수를 인위적으로 만들지 않는다.

## 24. 랭킹 결정 규칙

동점 처리도 결정적으로 정의한다.

```text
1차: entryScore 내림차순
2차: signalScore 내림차순
3차: 최근 실제 GC가 있는 종목 우선
4차: OBV·ADL 동시 확인 우선
5차: RVOL 높은 종목 우선
6차: 종목코드 오름차순
```

결과는 실행 시점이나 배열 입력 순서에 따라 달라지면 안 된다.

## 25. 진입 후보 상태

후보 상태는 점수와 별도로 관리한다.

| 상태 | 의미 |
|---|---|
| `WATCH` | 신호는 있으나 진입 조건 미완성 |
| `READY` | 기술 신호와 가격 전략 모두 충족 |
| `CHASING_RISK` | 상승했으나 현재 진입 위치가 불리함 |
| `OVERBOUGHT` | 과매수로 신규 진입 부적합 |
| `INVALIDATED` | 최신 데이터 또는 유니버스 조건 무효 |
| `NO_CANDIDATE` | 조건 충족 종목 없음 |

최종 추천 목록에는 기본적으로 `READY`만 포함한다. `WATCH`는 별도 관찰 목록으로 분리한다.

## 26. 성능 목표

로컬 DB 기준 목표를 다음과 같이 둔다.

- 동일 데이터 스냅샷의 반복 분석: 결과 캐시 사용
- 캔들 조회: 종목별 단건 조회 금지
- 지표 계산: 종목별 전체 이력 재조회 금지
- DB upsert: 단건 반복 대신 batch 처리
- KIS 호출: stale 종목만 요청
- 동일 작업 중복 실행: advisory lock으로 차단
- 실패 종목: 전체 작업을 중단하지 않고 retry queue로 분리

성능 측정값:

```text
dbReadMs
kisFetchMs
dbUpsertMs
indicatorComputeMs
rankingMs
totalDurationMs
cacheHit
```

- 지표 중복 가중치가 제한됨

## 28. 정책 변경 관리

분석 정책은 코드에 흩어져 있는 상수가 아니라 버전이 있는 설정으로 관리한다.

정책에 포함되는 항목:

- timeframe
- indicator periods
- Bollinger multiplier
- score weights
- stale threshold
- minimum history
- overbought thresholds
- minimum risk/reward ratio
- completed-candle policy

정책 변경 시 다음 값을 새로 생성한다.

```text
policyVersion
policyHash
changedAt
changedBy
changeReason
```

기존 결과를 새 정책 결과로 덮어쓰지 않는다. 이전 결과는 정책 버전과 함께 보존하거나 명확히 무효화한다.

## 29. 데이터 계보와 감사성

후보 결과에서 원본 데이터까지 역추적할 수 있어야 한다.

```text
result
→ signal
→ indicator point
→ normalized candle
→ raw KIS payload
```

종목별로 다음을 기록한다.

- 분석 ID
- 데이터 기준 시각
- 사용한 봉의 거래일
- 사용한 봉의 `fetched_at`
- 데이터 출처
- 계산 버전
- 적용 정책 해시
- 제외·경고 사유

사용자에게 표시하지 않는 원본 payload도 관리자 디버깅 경로에서 확인 가능해야 한다.

## 30. 안전한 장애 동작

외부 API나 DB 장애가 발생해도 오래된 데이터를 최신 데이터처럼 출력하지 않는다.

| 장애 | 동작 |
|---|---|
| KIS 인증 실패 | 해당 데이터 갱신 중단, 기존 결과는 stale 표시 |
| KIS rate limit | 공통 throttle·backoff 후 retry |
| KIS 응답 파싱 실패 | 저장하지 않고 `FAILED` 기록 |
| DB 읽기 실패 | 분석 중단, 오류 응답 반환 |
| DB upsert 일부 실패 | 해당 batch만 retry |
| 캘린더 확인 실패 | 최신성 `UNKNOWN`, 후보 제외 |
| 정책 로드 실패 | 안전한 기본 정책 사용 여부를 명시하거나 실행 중단 |

장애 시 빈 결과를 정상적인 “후보 없음”으로 위장하지 않는다.

## 31. 알림과 운영 임계치

다음 상황은 관리자 관찰 대상이다.

- 최신성 미충족 종목 비율 급증
- KIS 실패율 임계치 초과
- retry queue 지속 증가
- DB upsert 지연 증가
- 데이터 품질 `INVALID` 비율 증가
- 이전 실행 대비 후보 수 급변
- 동일 종목의 신호가 짧은 시간에 반복 변경

운영 로그에는 민감한 인증 정보와 전체 raw payload를 남기지 않는다.

## 32. 결과 이상 감지

분석 결과 자체도 회귀 감시 대상이다.

다음 통계를 이전 실행과 비교한다.

- 활성 종목 수
- 분석 완료 종목 수
- stale·invalid·failed 비율
- 후보 수
- 평균·최저·최고 점수
- 실제 GC 비율
- 과매수 제외 비율
- 평균 RVOL

급격한 변화가 발생하면 결과를 자동 확정하지 않고 `ANOMALY_REVIEW_REQUIRED`로 표시할 수 있어야 한다.

## 33. 성능 회귀 테스트

기능 정확도뿐 아니라 성능도 로컬 DB에서 검증한다.

테스트 항목:

- 100개·1,000개·전체 유니버스 처리 시간
- DB 읽기 쿼리 횟수
- KIS 호출 횟수
- batch upsert 횟수
- 메모리 사용량
- 결과 캐시 적중률
- retry 발생 시 추가 처리 시간

다음 회귀를 허용하지 않는다.

- 종목 수에 비례한 DB 단건 조회 증가
- 동일 snapshot에서 KIS 중복 호출
- 모든 종목 갱신으로 인한 stale 필터 무력화
- 결과 캐시 사용 후에도 전체 지표 재계산
- 실패 종목 때문에 전체 작업 재시작

## 34. 보안 및 권한

- KIS 토큰·appkey·appsecret은 결과와 로그에 노출하지 않는다.
- 관리자용 raw 응답은 관리자 인증 후에만 제공한다.
- 분석 결과 API는 입력 종목 수와 기간을 제한한다.
- 사용자 입력 종목코드는 시장별 형식 검증 후 조회한다.
- SQL은 파라미터 바인딩을 사용한다.
- raw payload는 화면 응답에 기본 포함하지 않는다.

## 36. 모듈별 책임 경계

기존 모듈을 다음 책임으로 유지한다.

| 책임 | 담당 영역 |

| KIS client | 인증·요청·throttle·재시도 |
| candle repository | 원본 캔들 정규화·upsert·조회 |
| freshness service | 종목별 최신 거래일·완료봉 판정 |

| signal service | 실제 교차·접근·신호 수명 |
| ranking service | 영역별 점수·위험 감점·순위 |

KIS client가 점수나 투자 판단을 수행하지 않으며, response mapper가 지표를 다시 계산하지 않는다.

## 37. API 입력 계약

분석 요청은 다음 입력을 사용한다.

```json
{
  "market": "KR",
  "codes": ["005930", "012330"],
  "timeframes": ["D", "W"],
  "minMarketCap": 30000000000,
  "completedOnly": true,
  "limit": 30,
  "policyVersion": "default"
}
```

검증 규칙:

- `codes`는 중복 제거
- 국내 코드는 6자리 숫자
- 해외 티커는 시장별 허용 형식 검증
- `limit`은 서버 최대값을 초과할 수 없음
- 지원하지 않는 timeframe은 거부
- 사용자 입력 정책은 허용된 범위로 clamp
- 비어 있는 종목 목록은 명확한 입력 오류로 응답

## 38. API 출력 계약

```json
{
  "ok": true,
  "analysisId": "...",
  "checkedAt": "...",
  "dataCutoffAt": "...",
  "policyVersion": "default",
  "indicatorVersion": "...",
  "statistics": {
    "requested": 2,
    "complete": 2,
    "stale": 0,
    "invalid": 0,
    "failed": 0,
    "qualified": 1
  },

```

`ok: true`는 요청 처리가 정상 완료됐다는 뜻이며, 후보가 있다는 뜻으로 해석하지 않는다. 후보가 없으면 `qualified = 0`과 `현재 진입 적합 종목 없음`을 함께 반환한다.

## 40. 상태 전이 검증

| 이전 상태 | 조건 | 다음 상태 |
|---|---|---|
| `BEFORE` | 간격 3봉 연속 축소 | `APPROACHING` |
| `APPROACHING` | 실제 교차 발생 | `CROSSED` |
| `CROSSED` | 후속 봉에서 추세·거래량 확인 | `CONFIRMED` |
| `CROSSED` | 과도한 급등·분배 발생 | `FAILED` |
| `CONFIRMED` | 최근성 만료 | `EXTENDED` |
| 모든 상태 | 최신성·데이터 품질 실패 | `INVALIDATED` |

상태 전이는 날짜 순서가 뒤바뀌거나 한 번의 실행에서 여러 단계를 건너뛰지 않는다.

## 41. 검증 매트릭스

| 영역 | 정상 | 경계 | 실패 |
|---|---|---|---|
| 유니버스 | 활성 보통주 | 거래량 회복 | 거래량 0 |
| 최신성 | 최신 완료봉 | 휴장일 | stale |
| EMA | 실제 교차 | 접근 중 | 이력 부족 |
| MACD | 교차·히스토그램 증가 | 간격 축소 | 계산 실패 |
| DMI/ADX | +DI 우위·ADX 상승 | ADX 20 미만 | ADX 하락 |
| OBV/ADL | 둘 다 상승 | 하나만 상승 | 둘 다 하락 |
| 거래량 | RVOL >= 1.2 | 0.7~1.2 | RVOL < 0.7 |
| 위험 | 정상 | 일부 경고 | 과매수·손익비 부족 |
| 응답 | 표·메타데이터 | 후보 없음 | 처리 실패 |

## 42. 배포 전 롤백 기준

다음 현상이 확인되면 새 분석 결과를 확정하지 않고 이전 안정 버전으로 되돌릴 수 있어야 한다.

- 후보 수가 이전 실행 대비 비정상적으로 급증 또는 급감
- 활성 종목 수가 정책 변경 없이 변동
- 최신 거래일보다 미래 날짜가 출력됨
- 거래량 0 종목이 후보에 포함됨
- 동일 스냅샷 재실행 결과가 달라짐
- KIS 호출량이 예상치를 초과
- DB batch 실패율 또는 retry queue가 지속 증가
- 기존 스캐너 API 응답 계약이 깨짐

롤백 시 데이터 자체를 삭제하지 않고 `analysisVersion`과 결과 상태만 이전 버전으로 전환한다.

## 43. 데이터 신선도 등급

신선도는 단순 통과·실패가 아니라 등급으로 관리한다.

| 등급 | 기준 |
|---|---|
| `FRESH` | 최신 완료 거래일과 일치 |
| `ACCEPTABLE` | 허용된 거래일 1회 이내 지연 |
| `STALE` | 허용 범위 초과 |
| `UNKNOWN` | 거래일 캘린더 또는 원본 상태 확인 불가 |

`STALE`과 `UNKNOWN`은 기술 지표를 계산할 수 있어도 최종 진입 후보에 포함하지 않는다.

## 44. 설명 가능성 규칙

각 점수는 원인을 역추적할 수 있어야 한다.

```json
{
  "contributions": [
    { "area": "TREND", "score": 16, "reasons": ["EMA9 crossed EMA20"] },
    { "area": "FLOW", "score": 18, "reasons": ["OBV and ADL rising"] }
  ],
  "deductions": [
    { "reason": "RSI near overbought", "score": -4 }
  ]
}
```

“점수가 높다” 또는 “지표가 좋다”만으로 설명하지 않는다. 실제 값·기준값·판정 결과를 함께 보존한다.

## 45. 호출량 및 비용 예산

분석 작업은 실행 전에 예상 비용을 계산한다.

```text
requestedSymbols
missingTimeframes
estimatedKisRequests
estimatedDbReads
estimatedDbWrites
```

다음 원칙을 적용한다.

- DB에 충분한 최신 데이터가 있으면 KIS를 호출하지 않음
- 동일 종목·동일 timeframe 요청 합치기
- 동일 실행 내 중복 KIS 요청 금지
- 호출 예산 초과 시 부족 데이터를 `DEFERRED`로 기록
- 전체 작업 실패 대신 checkpoint와 retry queue 사용

## 46. 분석 SLO

운영 지표를 다음처럼 관리한다.

| 지표 | 목표 |
|---|---|
| 최신 데이터 충족률 | 99% 이상 |
| 후보 응답 성공률 | 99% 이상 |
| KIS rate-limit 오류율 | 1% 미만 |
| DB batch 실패율 | 1% 미만 |
| 동일 요청 캐시 적중률 | 50% 이상 |
| 결과 재현성 | 동일 snapshot 100% |

목표 미달 시 기능 개선보다 먼저 원인과 영향 범위를 기록한다.

## 47. 시간대와 날짜 정규화

모든 저장·계산·표시의 시간 기준을 구분한다.

```text
거래일: 거래소 현지 시장일
저장 시각: UTC timestamptz
표시 시각: Asia/Seoul
```

거래일 문자열을 서버 로컬 시간으로 변환해 임의로 다음 날로 바꾸지 않는다. 미국 거래일이 한국시간 다음 날에 종료되는 경우에도 거래일과 저장 시각을 분리한다.

## 48. 데이터 계보 식별자

원본부터 응답까지 공통 식별자를 전달한다.

```text
sourceRequestId
sourcePayloadHash
normalizedCandleId
indicatorCalculationId
analysisId
```

같은 원본 payload가 중복 수신되면 중복 계산을 줄이고, 값이 달라졌을 때만 파생 결과를 무효화한다.

## 49. 캐시 무효화 순서

데이터 갱신 시 캐시는 다음 순서로 무효화한다.

```text
캔들 upsert
→ 캔들 조회 캐시 무효화
→ 지표 캐시 무효화
→ 후보 결과 캐시 무효화
→ 새 analysis snapshot 생성
```

중간 단계가 실패하면 이전에 검증된 결과를 삭제하지 않고 `STALE`로 표시한다.

## 50. 권한과 개인정보 경계

분석 결과와 운영 데이터의 접근 범위를 분리한다.

- 일반 결과: 종목·지표·판정·메타데이터만 제공
- 관리자 결과: 원본 payload·실패 상세·호출 통계 제공
- 인증정보: 어떠한 응답·로그에도 포함하지 않음
- 사용자 입력 종목 목록: 분석 작업 범위 외 목적으로 저장하지 않음
- raw payload 다운로드: 관리자 인증과 명시적 요청 필요

## 51. 운영 실행 모드

분석 실행은 목적에 따라 모드를 명시한다.

| 모드 | 목적 | KIS 호출 |
|---|---|---|
| `CACHE_ONLY` | 기존 DB 검증 | 금지 |
| `STALE_REFRESH` | 부족한 데이터 보충 | stale만 |
| `FULL_REBUILD` | 계산 버전 변경 | 허용 범위 내 |
| `DRY_RUN` | 대상·호출량 검증 | 금지 |
| `RETRY_FAILED` | 실패 종목 재처리 | 실패 종목만 |

운영 기본값은 `STALE_REFRESH`로 한다. `FULL_REBUILD`는 관리자 승인과 예상 호출량 확인 후에만 실행한다.

## 52. 최종 문서 품질 기준

문서는 다음 질문에 코드와 동일한 답을 제공해야 한다.

- 어떤 종목이 분석 대상인가?
- 어느 거래일의 어떤 봉을 사용했는가?
- 해당 봉은 완료됐는가?
- 지표는 어떤 공식과 버전으로 계산됐는가?
- 골든크로스는 실제 교차인가, 접근 중인가?
- 점수와 감점의 근거는 무엇인가?
- 왜 후보에서 제외됐는가?
- 결과는 언제 만료되는가?
- 실패 시 어떻게 재시도되는가?
- 동일 조건을 다시 실행하면 같은 결과가 나오는가?

## 53. 장시간 작업 제어

전체 유니버스 분석은 단일 요청의 실행 시간에 의존하지 않는다.

작업을 다음 단위로 나눈다.

```text
analysisJob
→ chunk
→ symbol task
→ timeframe task
```

각 단위는 다음 상태를 가진다.

```text
QUEUED → PROCESSING → SUCCEEDED
                    → RETRYING
                    → FAILED
                    → DEFERRED
```

checkpoint에는 마지막 처리 위치가 아니라 종목·timeframe별 상태를 저장한다. 종목 정렬이나 유니버스 변경으로 인해 위치 기반 재개가 잘못되는 것을 방지한다.

## 54. Backpressure와 큐 용량

생산 속도와 저장 속도가 다를 때 메모리에 작업을 무제한 적재하지 않는다.

- KIS 요청 큐 최대 크기 제한
- DB upsert 큐 최대 크기 제한
- 큐가 가득 차면 생산 워커 일시 정지
- batch 완료 후 생산 재개
- 메모리 큐 초과 작업은 `DEFERRED`로 DB 기록

큐의 현재 길이, 대기 시간, 처리량을 운영 통계로 기록한다.

## 55. KIS 회로 차단기

KIS 장애가 연속되면 호출을 계속 반복하지 않는다.

```text
CLOSED → OPEN → HALF_OPEN → CLOSED
```

- `CLOSED`: 정상 요청
- `OPEN`: 연속 rate-limit·인증·게이트웨이 오류로 일시 차단
- `HALF_OPEN`: 제한된 probe 요청
- 성공: `CLOSED`
- 실패: `OPEN` 유지

회로 차단 중인 종목은 오래된 데이터를 최신으로 표시하지 않고 `DEFERRED` 또는 `STALE`로 남긴다.

## 56. 멱등성 보장

동일 작업이 재실행되어도 데이터가 중복되거나 신호가 누적되지 않아야 한다.

멱등성 키:

```text
market
code
timeframe
candleDate
analysisId
indicatorVersion
policyHash
```

DB 저장은 기존 unique key와 upsert를 사용한다. 분석 결과·신호·알림도 동일한 외부 키로 중복 생성하지 않는다.

## 57. 스키마 변경 호환성

분석 기능 변경은 expand → migrate → contract 순서로 진행한다.

```text
1. 새 컬럼·새 버전 필드 추가
2. 기존 코드와 새 코드가 함께 읽을 수 있도록 전환
3. 데이터 backfill 및 로컬 DB 검증
4. 새 코드 활성화
5. 사용하지 않는 구조 제거
```

기존 캔들·유니버스 데이터를 파괴적으로 삭제하지 않는다. migration은 중복·NULL·기존 데이터 호환성을 먼저 검증한다.

## 58. 재처리 정책

실패 유형별 재처리 방법을 구분한다.

| 유형 | 재처리 |
|---|---|
| 인증 만료 | 토큰 모듈에서 1회 갱신 후 재시도 |
| rate limit | adaptive backoff 후 retry |
| 일시적 HTTP 오류 | 제한 횟수 retry |
| 잘못된 입력 | retry 금지, `INVALID` |
| 데이터 없음 | 거래일 재확인 후 `NO_DATA` |
| DB 일시 오류 | batch 단위 retry |
| 계산 오류 | 원본 보존 후 계산만 재실행 |

무한 재시도하지 않으며 최대 시도 횟수와 마지막 오류를 저장한다.

## 59. 데이터 보존 정책

데이터 종류별 보존 기간을 구분한다.

- 원본 KIS payload: 운영·감사에 필요한 기간 보존
- 정규화 캔들: 분석에 필요한 기간 이상 보존
- 지표 캐시: 계산 버전 변경 전까지 보존
- 실패 이력: 운영 분석 기간 동안 보존
- 임시 작업 상태: 완료 후 제한 기간 보존

보존 기간이 지난 데이터는 관련 계보와 감사 기록을 잃지 않는 방식으로 정리한다.

## 60. 동시성 정책

동시성은 워커 수가 아니라 외부 API와 DB의 허용량을 기준으로 정한다.

```text
KIS concurrency
DB write concurrency
indicator CPU concurrency
```

각각 독립적으로 설정하되 전체 계정 KIS throttle과 DB connection pool을 초과하지 않는다. 동시성 값을 높이는 것만으로 성능 개선으로 간주하지 않는다.

## 61. 캐시 일관성 검증

캐시를 반환하기 전에 최소한 다음을 확인한다.

- 정책 해시 일치
- 계산 버전 일치
- dataCutoffAt 유효
- 유니버스 버전 일치
- 최신성 등급이 `FRESH` 또는 허용된 `ACCEPTABLE`
- 후보 종목의 활성 상태 유지

검증 실패 시 캐시를 사용하지 않고 stale refresh 또는 재계산으로 전환한다.

## 62. 성능 측정 해석

총 처리 시간이 줄어도 KIS 호출량이나 DB 부하가 과도하게 증가하면 최적화로 인정하지 않는다.

최적화 전후에 함께 비교한다.

```text
totalDurationMs
perSymbolDurationMs
kisRequests
kisRetryCount
dbQueries
dbBatchSize
dbWriteMs
cacheHitRate
memoryPeak
failureRate
```

성능 개선은 다음 조건을 함께 만족해야 한다.

- 결과 정확도 저하 없음
- 최신성 저하 없음
- KIS 호출 예산 초과 없음
- DB 오류율 증가 없음
- 메모리 사용량 안정

## 63. 운영 변경 승인

다음 변경은 일반 코드 수정이 아니라 운영 정책 변경으로 취급한다.

- 점수 가중치 변경
- 과매수 기준 변경
- 최소 시가총액 변경
- 거래량 0 활성 정책 변경
- timeframe·최신성 기준 변경
- KIS 동시성 또는 retry 한도 변경
- 결과 후보 상한 변경

정책 변경 전후의 로컬 DB 비교 결과와 영향 종목 수를 기록한 후 적용한다.

## 64. 역할별 책임과 승인

분석 정책과 실행 결과의 책임을 분리한다.

| 역할 | 책임 |
|---|---|
| 데이터 담당 | KIS 원본·거래일·정규화 검증 |
| 계산 담당 | 지표 공식·초기값·버전 관리 |
| 전략 담당 | 점수·필터·진입 상태 정의 |
| 운영 담당 | 호출량·장애·retry·SLO 관찰 |
| 검수 담당 | 로컬 DB 재현·결과 표·회귀 검증 |

한 사람이 여러 역할을 맡더라도 변경 기록에는 각 승인 항목을 구분해 남긴다.

## 65. 변경 영향 분석

변경 전 영향 범위를 확인한다.

```text
정책 변경
→ 영향 지표
→ 영향 timeframe
→ 영향 API
→ 영향 캐시
→ 영향 알림
→ 필요한 migration·backfill
```

다음 변경은 결과 수와 기존 후보 목록의 차이를 비교한다.

- 지표 공식
- timeframe
- 최신성 기준
- 활성 종목 정책
- 시가총액 하한
- 거래량 기준
- 점수 가중치

## 66. 계약 테스트

모듈 간 연결은 구현 세부사항이 아니라 계약으로 테스트한다.

- KIS 응답 → 정규화 캔들 계약
- 캔들 저장 → 캔들 조회 계약
- 캔들 조회 → 지표 계산 계약
- 지표 계산 → 신호 계약
- 신호 → 랭킹 계약
- 랭킹 → 응답 DTO 계약

계약 테스트는 정상 응답뿐 아니라 필드 누락·빈 배열·잘못된 날짜·거래량 0·API 오류를 포함한다.

## 67. 데이터 품질 대시보드

관리자 화면 또는 디버그 API에서 다음을 확인할 수 있어야 한다.

- 시장별 활성 종목 수
- 보통주·비보통주 수
- 최신 거래일별 종목 수
- 거래량 0 종목 수
- stale·unknown 종목 수
- timeframe별 캔들 수
- 종목별 이력 부족 수
- KIS 실패율
- retry queue 크기
- 최근 batch 처리 시간
- 최근 분석 후보 수

품질 통계는 분석 결과와 별도로 조회할 수 있어야 한다.

## 68. 데이터 품질 게이트

분석 실행 전에 전체 품질 게이트를 통과해야 한다.

```text
활성 유니버스 확인
→ 최신 거래일 확인
→ 거래량 0 필터 확인
→ timeframe별 이력 확인
→ KIS·DB 오류율 확인
→ 품질 임계치 통과
→ 분석 실행
```

게이트 실패 시 부분 결과를 정상 결과로 반환하지 않고, 실패한 게이트와 영향 범위를 반환한다.

## 69. 백필과 재계산 정책

과거 데이터 보정은 실시간 갱신과 분리한다.

| 작업 | 실행 모드 |
|---|---|
| 최신 봉 보충 | `STALE_REFRESH` |
| 실패 종목 재시도 | `RETRY_FAILED` |
| 과거 누락 보정 | `BACKFILL` |
| 계산식 변경 | `FULL_REBUILD` |
| 결과 확인만 | `DRY_RUN` |

`BACKFILL`과 `FULL_REBUILD`는 운영 기본 작업에 포함하지 않는다. 예상 호출량·예상 소요 시간·DB 영향량을 먼저 산출한다.

## 70. 응답 안정성

응답 필드는 임의로 삭제하거나 의미를 변경하지 않는다.

- 새 필드는 optional로 먼저 추가
- 기존 필드 의미 변경 시 새 버전 DTO 사용
- 실패·후보 없음·데이터 stale을 서로 다른 상태로 반환
- 표 표시용 값과 계산용 원시값을 구분
- 티커 문자열은 표준화된 결과에서 생성

기존 화면이 새 응답 필드를 인식하지 못해도 기본 렌더링이 깨지지 않아야 한다.

## 71. 운영 종료 조건

다음 조건이면 분석 작업을 조기 종료할 수 있다.

- 품질 게이트 실패
- KIS 회로 차단기 OPEN
- DB 연결 풀 고갈
- 작업 시간 예산 초과
- retry 대상이 전체의 허용 비율 초과
- 결과 스냅샷을 고정할 수 없음

조기 종료 시 이미 저장된 정상 원본은 보존하고, 작업 상태를 `DEFERRED` 또는 `FAILED`로 기록한다.

## 72. 최종 운영 원칙

```text
최신성보다 정확성 우선
정확성보다 재현성 우선
재현성보다 데이터 계보를 우선하지 않으며 모두 충족해야 함
```

어떤 종목을 후보로 선택했는지뿐 아니라, 왜 다른 종목을 제외했는지도 설명할 수 있어야 한다. 확인할 수 없는 데이터는 추정하지 않고 명시적으로 제외한다.

## 73. 기준일 재현 분석

과거 기준일의 결과를 다시 계산할 수 있어야 한다.

```text
asOfTradingDate
dataCutoffAt
universeVersion
policyVersion
indicatorVersion
```

재현 분석은 기준일 이후에 저장된 캔들·유니버스·시가총액·정책을 사용하지 않는다. 현재 결과와 과거 결과를 혼동하지 않도록 응답에 `analysisMode: CURRENT | HISTORICAL`을 포함한다.

## 74. 결정 감사 로그

후보 선정과 제외를 같은 방식으로 기록한다.

```json
{

  "market": "KR",
  "code": "012330",
  "decision": "QUALIFIED",
  "statusBefore": "APPROACHING",
  "statusAfter": "READY",
  "score": 74,
  "quality": "A",
  "includedReasons": [],
  "excludedReasons": [],
  "dataRefs": []
}
```

후보가 아니었던 종목도 최소한 다음 중 하나의 제외 사유를 가진다.

```text

INSUFFICIENT_HISTORY
OVERBOUGHT
LOW_VOLUME
WEAK_TREND
NEGATIVE_FLOW
UNFAVORABLE_RISK_REWARD
```

## 75. 기준일 고정 테스트 픽스처

지표 테스트는 현재 DB 상태에 의존하지 않는다. 날짜가 고정된 로컬 fixture를 사용한다.

fixture에는 다음을 포함한다.

- 거래일이 연속된 정상 봉
- 휴장일이 포함된 봉
- 실제 EMA 골든크로스 사례
- 접근 중이지만 미교차인 사례
- 거래량 0 사례
- OBV·ADL 충돌 사례
- 과매수 사례
- 손익비 부족 사례
- OHLC 이상치 사례

동일 fixture와 동일 버전이면 운영 환경과 무관하게 동일한 지표·상태·점수가 나와야 한다.

## 76. 정책 실험과 운영 정책 분리

실험 정책은 운영 정책을 직접 덮어쓰지 않는다.

```text
EXPERIMENTAL
→ 결과 비교
→ 로컬 DB 검증
→ 영향 종목 검토
→ 승인
→ PRODUCTION
```

실험 결과에는 운영 결과와 구분되는 `policyMode`를 표시한다. 실험 정책으로 생성한 결과를 운영 알림이나 자동 전송에 사용하지 않는다.

## 77. 결과 비교 리포트

정책·계산 버전 변경 시 이전 버전과 다음을 비교한다.

- 신규 후보
- 탈락 후보
- 점수 변화
- 상태 변화
- 데이터 품질 변화
- 위험 플래그 변화
- KIS 호출량 변화
- 처리 시간 변화

변경 영향이 임계치를 초과하면 자동 배포하지 않고 검토 상태로 남긴다.

## 78. 데이터 정합성 주기 점검

운영 중에도 주기적으로 다음을 검사한다.

- 유니버스에는 있으나 캔들이 없는 종목
- 캔들은 있으나 유니버스에서 비활성인 종목
- 동일 키 중복 레코드
- timeframe별 날짜 역전
- 기간 종료일과 거래일 불일치
- 원본·정규화 값 불일치
- 계산 캐시와 원본 버전 불일치

정합성 오류는 자동으로 원본을 삭제하지 않고 관리자 검토 큐에 기록한다.

## 79. 운영 결과 보존

최종 후보 결과를 매번 덮어쓰지 않고 분석 단위로 보존한다.

- 분석 ID
- 생성 시각
- 기준일
- 정책·계산 버전
- 후보 목록
- 제외 통계
- 데이터 품질 통계
- 오류·retry 통계

이를 통해 “당시 왜 이 종목이 후보였는가”를 나중에 재확인할 수 있어야 한다.

## 80. 최종 승인 조건

다음 조건을 만족하면 해당 분석 설계를 운영 기준으로 승인한다.

- 현재·과거 기준일 결과를 재현할 수 있음
- 후보·비후보 결정 사유를 모두 설명할 수 있음
- 동일 입력에서 결과가 결정적으로 동일함
- 활성·거래량·최신성 정책이 일관되게 적용됨
- KIS·DB·계산·응답 책임이 분리됨
- 정책 변경 영향 리포트가 생성됨
- 로컬 DB fixture와 실제 DB 검증이 모두 통과함
- 장애·재시도·롤백 경로가 확인됨

## 81. 장애 대응 Runbook

### KIS 오류

1. 오류 유형을 인증·rate limit·일시 오류·영구 오류로 분류한다.
2. 인증 오류는 토큰 모듈의 단일 갱신 경로만 사용한다.
3. rate limit은 throttle 간격을 늘리고 작업을 `DEFERRED`로 분산한다.
4. 영구 오류는 재시도하지 않고 종목별 실패 사유로 기록한다.
5. 정상 확인 전에는 stale 데이터를 최신 후보로 승격하지 않는다.

### DB 오류

1. 실패한 batch만 재시도한다.
2. 이미 성공한 batch를 전체 재실행하지 않는다.
3. checkpoint와 멱등성 키를 기준으로 중복 저장을 방지한다.
4. 연결 풀 고갈 시 신규 작업을 중단하고 원인을 기록한다.

### 계산 오류

1. 원본 캔들은 보존한다.
2. 오류 종목만 `INVALID`로 격리한다.
3. 계산 버전과 입력 봉 식별자를 기록한다.
4. 수정 후 계산 단계만 재실행한다.

## 82. 알림 중복 방지

동일 종목·동일 신호·동일 기준일에 대해 알림을 반복 발송하지 않는다.

```text
market
code
timeframe
signalType
signalDate
policyVersion
```

알림은 상태가 다음과 같이 변경될 때만 발송한다.

```text
APPROACHING → CROSSED
CROSSED → CONFIRMED
CONFIRMED → FAILED
```

단순 polling이나 동일 결과 재계산만으로 새 알림을 만들지 않는다.

## 83. 쿼리 검증 기준

대량 분석 쿼리는 로컬 DB에서 실행 계획을 확인한다.

- 종목별 단건 조회 반복 금지
- timeframe·종목·거래일 인덱스 사용 확인
- 불필요한 전체 테이블 정렬 금지
- 대량 `OFFSET` 페이지네이션 금지
- 가능하면 keyset 또는 checkpoint 사용
- 분석에 필요한 컬럼만 조회
- 원본 payload는 기본 분석 쿼리에서 제외

실행 계획 변경으로 sequential scan이 발생하면 배포 전에 원인을 해결한다.

## 84. 인덱스 관리

핵심 조회 패턴에 맞는 인덱스를 유지한다.

```text
(market, code, timeframe, candle_date DESC)
(market, code, timeframe, fetched_at DESC)
(enabled, instrument_type, market, code)
```

인덱스 추가 전에는 기존 인덱스와 중복 여부, 쓰기 비용, 실제 사용률을 확인한다. 인덱스 이름과 migration 버전은 문서와 일치시킨다.

## 85. 성능 예산

분석 요청에 예산을 부여한다.

```text
maxSymbols
maxCandleRowsPerSymbol
maxKisRequests
maxDbReadMs
maxDbWriteMs
maxTotalDurationMs
```

예산을 초과하면 전체 시스템을 압박하지 않고 남은 작업을 `DEFERRED`로 저장한다. 성능 예산을 초과한 결과는 정상 완료로 표시하지 않는다.

## 86. 배포 후 검증

배포 직후 소량의 canary 대상만 분석한다.

```text
1. 대표 국내 종목
2. 대표 해외 종목
3. 데이터 부족 종목
4. 거래량 0 종목
5. 최근 골든크로스 종목
```

검증 항목:

- 응답 스키마 호환성
- 최신 거래일·갱신 시각
- 활성 필터
- 지표 계산 결과
- 후보 수 변화
- KIS 호출량
- DB batch 성공 여부
- 알림 중복 여부

Canary 검증 전에는 전체 유니버스 분석과 자동 알림을 활성화하지 않는다.

## 87. 감사 로그 보존과 접근

감사 로그는 분석 결과와 분리해 보존한다.

- 결과를 생성한 사용자·작업 유형
- 정책과 계산 버전
- 입력 종목 목록의 해시
- 데이터 기준 시각
- 결정·제외 사유
- 오류와 재처리 이력

로그 조회 권한은 관리자에게만 부여하고, 인증정보·불필요한 개인정보·민감한 원본 값은 기록하지 않는다.

## 88. 운영 대시보드 최소 패널

운영 화면은 다음 패널을 제공해야 한다.

1. 최신성: timeframe별 최신 거래일과 stale 비율
2. 품질: complete·partial·invalid·failed 비율
3. 호출: KIS 요청·재시도·rate limit 현황
4. 저장: DB batch 수·성공률·평균 지연
5. 분석: 후보 수·점수 분포·위험 플래그
6. 작업: queued·processing·deferred·failed 현황
7. 변경: 정책·계산 버전과 최근 영향 리포트

운영 대시보드의 수치는 분석 결과와 동일한 `dataCutoffAt`을 사용해야 한다.

## 89. 데이터 Drift 감지

시장의 구조나 KIS 응답 형식이 바뀌면 자동으로 감지한다.

감시 항목:

- 시장별 종목 수 급변
- 평균·중앙 거래량 급변
- 가격 0 또는 결측 비율 증가
- KIS output 필드 구조 변경
- 최신 거래일 분포 이상
- timeframe별 봉 수 급변
- 후보 수와 점수 분포 급변

Drift가 감지되면 신규 후보를 자동 확정하지 않고 `DATA_DRIFT_REVIEW` 상태로 보낸다.

## 90. 계산 위험 통제

지표 계산은 투자 판단을 보장하지 않는다. 결과에 계산 한계와 위험 플래그를 함께 표시한다.

- 과거 데이터 기반 신호는 미래 수익을 보장하지 않음
- 진행 중 봉은 완료봉 신호와 구분
- 거래량이 낮은 종목은 기술 신호 신뢰도 하향
- 급격한 가격 변동은 진입 점수와 별도로 경고
- 가격 제한·거래정지·시장 이벤트는 기술 지표만으로 판단하지 않음

위험 플래그가 있으면 점수와 무관하게 `CAUTION` 또는 `EXCLUDED` 상태를 부여할 수 있다.

## 91. 용량 계획

유니버스가 증가해도 처리 구조가 단일 서버 메모리에 종속되지 않도록 한다.

계획 기준:

- 일·주·월봉별 예상 캔들 행 수
- 원본 payload 저장량
- 지표 캐시 증가량
- DB connection pool 사용량
- KIS 요청 예산
- 작업 chunk 수와 평균 처리 시간
- retry queue 최대 적체량

용량 한계에 접근하면 신규 작업을 자동으로 `DEFERRED` 처리하고 관리자에게 알린다.

## 92. 재해 복구

원본과 파생 결과를 복구 순서에 따라 분리한다.

```text
1. 유니버스 복구
2. Raw·Normalized 캔들 복구
3. 정책·계산 버전 복구
4. Derived 지표 재계산
5. 후보 결과 재생성
6. 알림 상태 검증
```

파생 캐시가 손상되어도 원본 캔들과 정책이 보존되어 있으면 재계산할 수 있어야 한다. 복구 후에는 최신성·정합성·멱등성 검사를 통과해야 운영 결과를 재개한다.

## 93. 작업 우선순위

처리 지연 시 모든 작업을 동일하게 처리하지 않는다.

| 우선순위 | 작업 |
|---|---|
| P0 | 현재 활성 종목의 최신 완료 일봉 |
| P1 | 최신 주봉·월봉 보충 |
| P2 | 실패 종목 retry |
| P3 | 과거 backfill |
| P4 | 계산 버전 전체 재생성 |

P0 작업이 지연되는 동안 P3·P4 작업을 실행하지 않는다.

## 94. 데이터·알림 원자성

후보 결과 저장과 알림 발송을 하나의 성공으로 취급하지 않는다.

```text
분석 결과 저장 성공
→ 알림 delivery queue 등록
→ 알림 전송
→ 전송 상태 확정
```

분석 결과가 저장되지 않은 상태에서 알림을 발송하지 않는다. 알림 실패는 분석 결과를 실패로 되돌리지 않고 별도 retry 상태로 관리한다.

## 95. 재현 가능한 운영 명령

관리자 작업은 실행 목적과 범위를 명시한다.

```text
analysis run --mode DRY_RUN --market KR
analysis run --mode STALE_REFRESH --timeframe D
analysis run --mode RETRY_FAILED --analysis-id ...
analysis run --mode HISTORICAL --as-of 20260828
```

실제 명령 체계가 도입되기 전에도 API·관리자 화면은 동일한 의미의 모드와 파라미터를 사용한다.

## 96. 품질·성능 수용 기준

새 기능은 정확도와 성능을 동시에 통과해야 한다.

```text
정확성 테스트 통과
AND
최신성 테스트 통과
AND
재현성 테스트 통과
AND
보안 테스트 통과
AND
성능 예산 통과
AND
장애·재시도 테스트 통과
```

하나라도 실패하면 기능은 실험 상태로 유지하며 운영 분석·자동 알림에 연결하지 않는다.

## 97. 입력 계약 및 호환성 관리

분석기는 KIS 응답을 직접 신뢰하지 않고, 수집 단계에서 버전이 있는 정규화 계약으로 변환한다.

- 필수 필드: 종목코드, 종목명, 거래일시, 시가, 고가, 저가, 종가, 거래량
- 선택 필드: 거래대금, 조정 여부, 시장 구분, 원천 갱신시각
- 필수 필드 누락은 계산 단계가 아니라 수집 검증 단계에서 차단
- 알 수 없는 필드는 보존하되 계산에는 사용하지 않음
- 계약 버전과 원천 응답 해시를 실행 메타데이터에 기록

계약 변경은 기존 버전 데이터를 재현할 수 있는 호환 계층 또는 명시적인 마이그레이션을 동반해야 한다.

## 98. Shadow 및 Canary 분석

정책·지표·점수식 변경은 기존 결과를 즉시 대체하지 않고 비교 실행한다.

```text
기존 계산
    ├─ 운영 결과 유지
    └─ 신규 계산(Shadow)
          └─ 결과 차이·성능·결측률 비교
```

신규 계산은 제한된 종목군에서 Canary로 실행하고, 다음 조건을 만족할 때만 전체 적용한다.

- 결과 차이가 설명 가능함
- 결측·제외율이 허용 범위 이내임
- 계산 시간과 KIS 요청량이 예산 이내임
- 기존 결과와의 회귀 검증 완료

## 99. 부분 실패와 완료 상태

시장 전체 작업은 일부 종목 실패만으로 전체 성공으로 표시하지 않는다.

작업 상태는 `SUCCESS`, `PARTIAL_SUCCESS`, `FAILED`, `CANCELLED`로 구분하고 다음을 함께 저장한다.

- 요청 종목 수
- 성공·실패·제외·보류 종목 수
- 실패 원인별 건수
- 마지막 성공 단계
- 재시도 가능 여부
- 결과 사용 가능 범위

`PARTIAL_SUCCESS` 결과는 화면과 API에서 완료율 및 데이터 기준시각을 함께 노출한다.

## 100. 거래일·세션 경계 검증

최신성 판정은 단순한 현재 날짜 비교가 아니라 시장별 거래일 캘린더와 세션 상태를 사용한다.

- 국내·해외 시장별 거래일 캘린더 분리
- 휴장일·공휴일·서머타임·조기 폐장 반영
- 진행 중 봉과 완료 봉 분리
- 거래일시와 데이터 갱신일시를 별도로 기록
- 시장이 닫힌 상태에서는 정상적인 마지막 완료봉을 최신 기준으로 인정

세션 판정이 불명확하면 후보 생성보다 `FRESHNESS_UNKNOWN`을 우선한다.

## 101. 분석 결과 계보(Lineage)

각 후보는 결과만 저장하지 않고 어떤 입력과 계산을 거쳤는지 추적 가능해야 한다.

```text
원천 응답
→ 정규화 봉
→ 지표 입력 구간
→ 지표 값·교차 판정
→ 점수·제외 규칙
→ 최종 후보
```

후보 상세에는 원천, 봉 기준시각, 갱신시각, 계산 버전, 정책 버전, 제외·경고 판정의 근거를 연결한다. 동일 실행을 다시 수행해도 같은 입력과 버전이면 같은 결과가 나와야 한다.

## 102. 안전한 롤백과 재처리

정책 또는 계산 버전 배포 시 이전 버전을 즉시 복구할 수 있어야 한다.

- 배포 전 현재 운영 버전 고정
- 신규 결과를 별도 실행 ID로 저장
- 승인 전 운영 결과와 알림 대상 변경 금지
- 롤백 시 신규 결과를 삭제하지 않고 무효화
- 실패 구간만 원본 기준으로 재처리

롤백은 코드 버전뿐 아니라 지표 파라미터, 유니버스 조건, 거래일 기준까지 함께 복원해야 한다.

## 103. 비용·자원 예산

성능 최적화는 처리 시간만이 아니라 외부 API와 DB 자원 사용량까지 포함해 평가한다.

실행별로 다음을 측정한다.

- KIS 요청 수와 요청 실패 수
- retry 및 rate-limit 대기 시간
- DB 조회·upsert 행 수
- peak 메모리와 동시 워커 수
- 종목당 평균 계산 시간
- 캐시 적중률

예산을 초과하면 병렬도를 높이지 않고 작업을 보류·축소하며, 운영자에게 원인과 영향 범위를 알린다.

## 104. 사용자 응답 완전성

분석 결과는 종목 목록만 반환하지 않는다. 결과를 소비하는 화면·API·자동화 모두 다음 공통 구조를 사용한다.

- 종목명·종목코드
- 시장·종목 유형·활성 상태
- 사용한 봉의 거래일시
- 각 봉 데이터의 갱신일시
- 분석 실행시각과 기준시각
- 최신성·결측·경고 상태
- 점수와 근거 지표
- 제외 또는 보류 사유

필수 메타데이터가 없는 결과는 추천 결과가 아니라 검증 실패 결과로 취급한다. 화면 표시 형식이 달라도 원본 API 계약의 의미와 값은 동일해야 한다.

## 105. 결과 승인 상태

계산이 완료되었다는 사실과 운영 추천으로 사용할 수 있다는 사실을 분리한다.

| 상태 | 의미 |
|---|---|
| `CALCULATED` | 계산은 완료되었으나 품질 검증 전 |
| `REVIEW_REQUIRED` | 드리프트·결측·정합성 검토 필요 |
| `APPROVED` | 화면 및 자동화 사용 가능 |
| `REJECTED` | 오류 또는 정책 위반으로 사용 불가 |
| `EXPIRED` | 기준시각이 지나 최신 결과로 사용할 수 없음 |

자동화 전송은 `APPROVED` 상태에서만 허용한다. 상태 변경 주체, 변경시각, 변경 사유를 함께 기록한다.

## 106. 결과 만료와 재검증

후보 결과는 영구적으로 유효하지 않으며 시장·timeframe별 유효기간을 갖는다.

- 일봉 결과: 다음 완료 일봉이 생성되면 재검증
- 주봉 결과: 다음 완료 주봉 또는 구성 종목 변경 시 재검증
- 월봉 결과: 다음 완료 월봉 또는 구성 종목 변경 시 재검증
- 원천 데이터 정정·정책 변경·계산 버전 변경 시 즉시 만료

만료된 결과는 삭제하지 않고 `EXPIRED`로 남겨 이력과 재현성을 보존한다.

## 107. 품질 회귀 기준선

코드·파라미터 변경은 기준 실행과의 차이를 자동 비교한다.

비교 항목:

- 유효 입력 봉 수
- 결측·제외·보류 비율
- 골든크로스 판정 수
- 최종 후보 수
- 후보별 점수 변화
- 상위 후보 순위 변화
- 종목별 계산 시간

허용 범위를 벗어난 차이는 기능 실패가 아니라도 `REGRESSION_REVIEW`로 분류하고 승인 전 배포를 중지한다.

## 108. 지표별 근거 보존

종합점수만 저장하면 사후 검증이 불가능하므로 모든 필수 지표의 원시 계산값과 판정을 함께 저장한다.

- 현재값과 직전값
- 교차 여부
- 접근 중 여부
- 계산에 사용한 기간과 봉 수
- 지표별 신뢰도·경고
- 점수 기여도
- 해당 지표가 제외된 경우의 사유

지표의 표시 순서가 바뀌어도 저장된 근거와 최종 점수는 달라지지 않아야 한다.

## 109. 데이터 정정 정책

거래소·KIS의 사후 정정으로 과거 봉이 바뀌는 경우 정정 전 결과를 덮어쓰지 않는다.

```text
정정 전 실행 결과 보존
→ 정정 원본 수신
→ 영향받은 timeframe·종목 식별
→ 해당 범위만 재계산
→ 새 실행 결과 생성
→ 기존 결과와 차이 기록
```

정정으로 후보가 추가·제거되면 알림 재발송 여부를 정책으로 결정하며, 동일 이벤트의 중복 전송은 허용하지 않는다.

## 110. 접근 제어와 민감정보 분리

분석 결과 조회, 정책 변경, 재처리, 승인, 알림 재전송은 서로 다른 권한으로 관리한다.

- 일반 사용자: 승인된 결과 조회
- 운영자: 실행·재처리·장애 확인
- 검토자: 후보 승인·반려
- 관리자: 정책·권한·보존기간 변경

KIS 인증정보와 원본 응답에 포함될 수 있는 민감정보는 분석 결과와 분리 저장한다. 로그·오류 응답·감사 기록에는 토큰, 앱 시크릿, 전체 인증 헤더를 남기지 않는다.

## 111. 알림 재전송 멱등성

알림 키는 종목코드만으로 만들지 않고 다음 조합으로 생성한다.

```text
market + instrumentCode + timeframe + analysisRunId + signalVersion + deliveryChannel
```

같은 키의 전송 요청은 한 번만 성공 처리한다. 전송 실패 재시도와 새로운 분석 실행은 구분하며, 사용자가 재전송을 요청한 경우에도 원래 이벤트와 재전송 이벤트를 감사 로그에 남긴다.

## 112. 운영 종료 조건

분석 작업은 무한 재시도하지 않는다. 다음 조건에서 안전하게 종료한다.

- 동일 원인 실패가 허용 횟수를 초과
- KIS rate limit 또는 장애 회로가 열림
- DB 쓰기 지연이 성능 예산을 초과
- 거래일·세션 판정이 불명확
- 필수 입력 봉이 부족
- 결과 승인에 필요한 검증을 완료하지 못함

종료 시 부분 결과를 성공으로 포장하지 않고, 실행 ID·중단 단계·미처리 범위·재개 가능 지점을 기록한다.

## 113. 최신성 SLA

최신성은 단일 기준이 아니라 시장·timeframe·작업 유형별 SLA로 관리한다.

각 실행은 다음을 산출한다.

- 기대 최신 거래일
- 실제 최신 거래일
- 지연 봉 수
- 마지막 성공 수집시각
- 마지막 성공 계산시각
- SLA 초과 여부

SLA를 초과한 결과는 점수와 무관하게 `STALE`로 표시하며, 최신 결과처럼 자동 전송하지 않는다. 휴장·조기 폐장 등 정상적인 지연은 거래일 캘린더 근거를 함께 저장한다.

## 114. 의존성 장애 전파 차단

외부 API, DB, 계산 워커, 알림 채널의 장애가 전체 분석으로 전파되지 않도록 경계를 둔다.

```text
KIS 장애 ─┐
DB 지연  ─┼→ 해당 단계 격리 → 재시도/보류 → 영향 범위 표시
알림 장애 ┘
```

수집 장애는 계산 결과를 새로 만들지 못하게 하지만 이미 승인된 결과의 조회까지 차단해서는 안 된다. 알림 채널 장애도 원본 분석 실행과 다른 채널의 전송을 중단시키지 않는다.

## 115. 테스트 매트릭스

테스트는 코드 단위가 아니라 시장·timeframe·데이터 상태의 조합으로 관리한다.

| 구분 | 정상 | 결측 | 중복 | 지연 | 정정 | 장애 |
|---|---:|---:|---:|---:|---:|---:|
| 국내 일봉 | 필수 | 필수 | 필수 | 필수 | 권장 | 필수 |
| 국내 주봉 | 필수 | 필수 | 필수 | 필수 | 권장 | 필수 |
| 국내 월봉 | 필수 | 필수 | 필수 | 필수 | 권장 | 필수 |
| 해외 일봉 | 필수 | 필수 | 필수 | 필수 | 권장 | 필수 |
| 해외 주봉 | 필수 | 필수 | 필수 | 필수 | 권장 | 필수 |
| 해외 월봉 | 필수 | 필수 | 필수 | 필수 | 권장 | 필수 |

각 테스트는 결과값뿐 아니라 상태, 메타데이터, 재시도, DB 멱등성까지 검증한다. 기능 테스트는 로컬 DB에서 먼저 통과한 뒤 공유·운영 환경에 적용한다.

## 116. 부하 단계와 우아한 성능 저하

처리량이 한계를 초과하면 무제한 병렬화를 하지 않고 단계적으로 부하를 줄인다.

1. 과거 backfill 중단
2. 저우선순위 timeframe 보류
3. 재시도 간격 확대
4. 신규 후보 계산 제한
5. P0 최신 완료봉만 처리

이 과정에서도 기존 승인 결과 조회와 실행 이력 조회는 유지한다. 부하 감소가 시작된 시각과 복구 조건을 기록한다.

## 117. 관측성 표준

모든 단계는 동일한 `runId`, `market`, `timeframe`, `instrumentCode`를 전달한다.

필수 관측 항목:

- 단계별 시작·종료시각
- 처리·성공·실패·보류 건수
- p50·p95 처리시간
- API 응답코드와 재시도 횟수
- DB 쿼리·upsert 지연
- 큐 적체량
- 최종 상태 전이

로그는 한 건의 종목을 재구성할 수 있어야 하지만 인증정보와 불필요한 원문 민감정보는 마스킹한다.

## 118. 장애 보고서와 재발 방지

운영 장애가 종료되면 원인만 기록하지 않고 탐지부터 복구까지의 전체 흐름을 남긴다.

- 영향받은 시장·timeframe·종목 범위
- 최초 발생·탐지·완화·복구시각
- 잘못 표시되거나 누락된 결과
- 외부 API·DB·코드·정책 중 원인 분류
- 임시 조치와 영구 조치
- 회귀 테스트 추가 여부
- 문서·알람·런북 갱신 여부

동일한 장애가 다시 발생하면 과거 보고서와 연결해 재발 여부와 해결 효과를 확인한다.

## 119. 분석 정책의 변경 이력

점수 가중치, 임계값, 제외 조건, 시장별 유니버스 정책은 코드와 별도로 버전 관리한다.

정책 변경에는 다음을 포함한다.

- 변경 전·후 값
- 변경 사유와 근거
- 영향 예상 범위
- 적용 예정시각
- 승인자
- 롤백 정책

정책 파일이 없거나 버전이 식별되지 않는 실행은 운영 후보를 생성할 수 없다.

## 120. 문서와 구현의 일치성

문서에 정의된 상태·필드·판정식·메타데이터는 구현과 자동 검증한다.

- API 스키마와 문서 필드 비교
- 상태값 enum 일치 검사
- 지표 파라미터와 계산 코드 비교
- 화면 표시 필수 메타데이터 검사
- 예제 명령의 실제 동작 여부 검사

문서만 갱신하거나 코드만 갱신한 상태를 허용하지 않는다. 변경 완료 조건은 구현, 테스트, 문서, 운영 절차가 같은 버전을 가리키는 것이다.

## 121. 실행 스냅샷

분석 실행은 실행 시점의 입력 범위를 고정해야 한다. 실행 중 유니버스나 정책이 바뀌어도 동일 실행의 결과가 달라지지 않아야 한다.

스냅샷에 포함할 항목:

- 활성 종목 목록과 종목 속성
- 각 종목의 입력 봉 범위
- 거래일 캘린더 버전
- 지표·점수·제외 정책 버전
- 원천 데이터 기준시각
- 실행 환경과 코드 버전

스냅샷이 완성되지 않은 실행은 재현 가능한 결과로 표시하지 않는다.

## 122. 중복 실행 방지

동일 시장·timeframe·기준시각에 대한 분석은 중복 실행하지 않는다.

```text
동일 실행 키 확인
→ 실행 중이면 기존 실행에 연결
→ 완료 상태면 결과 재사용
→ 실패 상태면 정책에 따라 재개 또는 새 실행
```

강제 재실행은 별도의 `forceReason`과 실행자를 요구한다. 중복 실행이 발생해도 후보·알림·upsert 결과가 중복 생성되지 않아야 한다.

## 123. 보존 기간과 삭제 감사

원본 봉, 정규화 봉, 지표, 후보, 알림 이력은 서로 다른 보존 기간을 가질 수 있다. 삭제·압축·아카이빙은 분석 재현성과 법적·운영 요구를 먼저 확인한다.

- 삭제 대상과 보존 사유를 사전 계산
- 실행·승인·알림 감사 기록은 원본 결과보다 짧게 보존하지 않음
- 보존 기간 만료 전 삭제 예정 알림
- 삭제 후에도 집계값과 삭제 감사 이벤트 보존

운영 데이터 정리는 분석 실행 중인 범위와 충돌하지 않도록 격리된 작업으로 수행한다.

## 124. 보안 감사 이벤트

분석 결과 자체뿐 아니라 운영자가 수행한 민감한 작업을 감사한다.

- 정책 변경
- 후보 승인·반려
- 결과 재처리·강제 실행
- 알림 재전송
- 데이터 삭제·복구
- 권한 변경

감사 이벤트에는 주체, 시각, 대상, 이전 상태, 이후 상태, 사유, 요청 식별자를 저장한다. 감사 기록은 일반 운영자가 수정하거나 삭제할 수 없어야 한다.

## 125. 오류 분류 표준

재시도 가능 오류와 즉시 중단 오류를 같은 방식으로 처리하지 않는다.

| 분류 | 예시 | 처리 |
|---|---|---|
| `TRANSIENT` | 일시적 네트워크·rate limit | 지수 백오프 재시도 |
| `AUTH` | 인증 만료·권한 오류 | 토큰 수명주기 경로에서 복구 |
| `VALIDATION` | 필수 필드·형식 오류 | 재시도 없이 격리 |
| `CONFLICT` | 중복 실행·버전 충돌 | 기존 실행 확인 후 재개 |
| `PERMANENT` | 지원하지 않는 요청 | 즉시 실패·운영자 알림 |
| `UNKNOWN` | 분류 불가 오류 | 보수적으로 중단·검토 |

오류 문자열만 저장하지 않고 안정적인 오류 코드와 원인 단계, 재시도 가능 여부를 함께 저장한다.

## 126. 화면 표시 일관성

동일 실행의 결과를 여러 화면에서 보여줄 때 순위·점수·상태가 서로 달라지지 않아야 한다.

- 서버가 확정한 정렬 순서를 클라이언트가 임의로 재정렬하지 않음
- 표시용 반올림과 내부 계산값을 구분
- 시간대와 기준시각을 동일한 형식으로 표시
- 종목명 변경 시 코드 기준으로 결과를 연결
- 비활성 종목은 과거 이력과 현재 후보를 구분하여 표시

화면은 누락된 데이터를 빈 문자열로 숨기지 않고 `미확인`, `지연`, `계산 불가` 등 상태를 명시한다.

## 127. 데이터 복구 검증 샘플

전체 복구가 완료되었다고 선언하기 전에 시장·timeframe·상태별 표본을 추출해 검증한다.

표본 검증 항목:

- 원본 봉과 파생 지표의 연결
- 최신 거래일과 갱신시각
- 점수·제외 조건 재계산 결과
- 승인·만료·알림 상태
- 복구 전후 결과 차이

표본 검증 실패 시 전체 복구를 성공으로 표시하지 않고 실패 범위를 확장 조사한다.

## 128. 최종 운영 체크리스트

운영 분석을 완료로 처리하기 전 다음을 모두 확인한다.

```text
유니버스 활성 상태 확인
→ 최신 완료봉·갱신시각 확인
→ 입력 계약·스냅샷 고정
→ 지표 계산·교차 판정 검증
→ 제외·경고 규칙 적용
→ DB 멱등 저장 확인
→ 결과 승인 상태 확인
→ 알림 큐·중복 키 확인
→ 실행 요약·감사 로그 기록
```

하나라도 확인되지 않으면 결과는 운영 완료가 아니라 `REVIEW_REQUIRED`로 남긴다.

## 129. 데이터 계보 무결성

결과 계보의 각 단계는 이전 단계의 식별자와 해시를 참조해야 한다.

```text
rawHash → normalizedHash → indicatorHash → scoreHash → resultHash
```

중간 데이터가 변경되면 이후 해시가 달라져야 하며, 연결이 끊긴 결과는 승인하지 않는다. 계보 검증은 실행 완료 시점과 결과 조회 시점 모두 수행할 수 있어야 한다.

## 130. 결과 비교의 기준 고정

두 실행의 결과를 비교할 때는 단순한 종목 목록 차이만 비교하지 않는다. 동일한 유니버스, 거래일 캘린더, 정책 버전, 입력 봉 범위를 기준으로 정렬한 뒤 비교한다.

필수 비교 결과:

- 신규·이탈 후보
- 점수 변화와 순위 변화
- 골든크로스 상태 변화
- 지표별 판정 변화
- 제외·보류 사유 변화
- 입력 데이터 차이와 계산 버전 차이

비교 기준이 다른 실행은 `NOT_COMPARABLE`로 표시한다.

## 131. 시장별 정책 격리

국내와 해외 시장은 거래일, 세션, 가격 단위, 거래량 의미, 휴장 규칙이 다르므로 공통 계산 모듈에 시장별 예외를 섞지 않는다.

- 시장별 캘린더 어댑터
- 시장별 원천 필드 매핑
- 시장별 종목 활성화 정책
- 시장별 최신성 SLA
- 시장별 알림·표시 정책

공통 지표 계산은 정규화 계약 이후에만 수행하고, 시장별 차이는 명시적인 정책 객체로 전달한다.

## 132. 파라미터 유효성 검증

EMA 기간, MACD 기간, RSI·MFI 기간, Bollinger 기간·배수, 임계값은 실행 전에 검증한다.

- 기간은 양의 정수이며 순서 제약을 만족해야 함
- 표준편차 배수와 점수 가중치는 허용 범위 내여야 함
- 모든 가중치 합계와 정규화 방식은 명시되어야 함
- 정책에 없는 파라미터는 기본값으로 묵시 처리하지 않음

유효하지 않은 파라미터는 일부 종목만 계산하지 않고 실행을 시작하기 전에 전체 작업을 차단한다.

## 133. 알림과 화면의 표현 일치

화면에서 `골든크로스`, `접근 중`, `경고`, `제외`로 표시한 의미는 알림 payload와 동일해야 한다.

- 동일한 signal 상태 코드 사용
- 표시용 문구는 상태 코드에서 변환
- 점수와 등급을 채널별로 임의 변경하지 않음
- 기준시각·최신성·위험 플래그를 알림에도 포함
- 알림 길이 제한으로 필드가 생략되면 생략 사실을 표시

채널별 포맷 차이는 허용하지만 의미와 핵심 수치는 변경할 수 없다.

## 134. 자동화 중단과 재개

자동화는 실패 후 무조건 재개하지 않고 중단 원인에 따라 재개 조건을 요구한다.

| 중단 원인 | 재개 조건 |
|---|---|
| 데이터 드리프트 | 원인 확인 및 기준선 갱신 |
| 인증 오류 | 인증 상태 정상화 및 단일 토큰 경로 확인 |
| DB 장애 | 쓰기·멱등성 검증 완료 |
| 계산 회귀 | 기준 실행 비교와 승인 |
| 큐 적체 | 적체량이 안전 한계 이하 |
| 캘린더 불일치 | 시장별 캘린더 버전 확정 |

재개 시 중단된 실행을 그대로 덮어쓰지 않고 재개 지점과 새 실행 ID를 기록한다.

## 135. 운영 데이터의 읽기 격리

분석 중간 상태가 사용자에게 완성 결과처럼 노출되지 않도록 실행 영역과 조회 영역을 분리한다.

- 계산 중인 결과는 임시 실행 영역에 저장
- 검증·승인 완료 후 조회 가능한 결과로 전환
- 이전 승인 결과는 신규 실행 실패와 무관하게 유지
- 전환은 실행 단위로 원자적으로 처리

이를 통해 부분 upsert나 중간 계산값이 화면·알림으로 유출되는 것을 방지한다.

## 136. 개선안 종료 기준

문서 개선은 항목 수를 늘리는 것으로 완료하지 않는다. 각 제안은 구현 위치, 테스트 방법, 운영 지표, 담당 책임을 가져야 한다.

개선 항목은 다음 상태 중 하나로 관리한다.

`PROPOSED` → `DESIGNED` → `IMPLEMENTED` → `TESTED` → `OPERATING` → `RETIRED`

상태가 `TESTED`에 머문 항목은 운영 자동화에 연결하지 않으며, `OPERATING` 항목은 실제 지표와 장애 이력을 기준으로 정기 재검토한다.

## 137. 승인 결과 동결

`APPROVED` 결과는 승인 이후 입력·정책·계산 결과가 임의로 바뀌지 않도록 동결한다.

- 승인된 결과의 입력 스냅샷과 해시 보존
- 수정이 필요하면 기존 결과를 덮어쓰지 않고 새 실행 생성
- 승인 결과에 대한 직접 update 금지
- 승인 취소는 상태 전이와 사유를 감사 로그에 기록

동결은 데이터베이스 권한과 애플리케이션 검증 양쪽에서 적용한다.

## 138. 기준선 데이터셋

품질·성능 회귀 검증에 사용하는 대표 데이터셋을 고정한다.

기준선은 다음 범위를 포함한다.

- 정상 거래일
- 휴장 직후 거래일
- 거래량 0 또는 결측 데이터
- 급등·급락 구간
- 종목명·상태 변경 구간
- 국내·해외 각 시장의 일·주·월봉

기준선 데이터는 임의로 갱신하지 않으며 갱신 시 기존 기준선과 신규 기준선을 모두 비교하고 변경 사유를 기록한다.

## 139. 결정론적 계산 검증

같은 입력과 같은 버전으로 여러 번 실행한 결과는 동일해야 한다.

- 부동소수점 반올림 규칙 고정
- 동일 점수의 정렬 tie-breaker 고정
- 시간대 변환 시각 고정
- 병렬 처리 순서가 결과에 영향을 주지 않도록 설계
- 난수·현재시각·외부 상태를 계산식에서 격리

결과가 달라지면 계산 오류로 간주하고 `NON_DETERMINISTIC` 상태로 격리한다.

## 140. 변경 영향 분석

변경을 적용하기 전에 어떤 결과와 운영 흐름이 영향을 받는지 식별한다.

```text
변경 항목
→ 영향 지표
→ 영향 timeframe·시장
→ 영향 API·화면
→ 영향 알림·자동화
→ 필요한 테스트·롤백 범위
```

영향 범위를 산출하지 못한 변경은 전체 운영에 배포하지 않고 제한된 Shadow 실행으로만 검증한다.

## 141. 데이터 품질 점수

종목별 입력 품질을 별도로 계산해 기술적 점수와 혼동하지 않는다.

품질 점수는 다음 요소를 반영한다.

- 필수 봉 충족률
- 최신성
- 가격·거래량 유효성
- 중복·역순 거래일 여부
- 원천 응답과 정규화 결과의 일치성
- 최근 정정 이력

품질 점수가 기준 미만이면 기술 지표가 좋아도 후보에서 제외하거나 `LOW_DATA_CONFIDENCE`를 표시한다.

## 142. 운영자 확인 포인트

자동 검증을 통과해도 외부 시장 상태나 데이터 이상이 의심되면 운영자가 확인할 수 있는 요약을 제공한다.

- 이전 실행 대비 후보 수 변화
- 시장별 실패·보류 종목
- 최신 거래일 분포
- 상위 후보의 경고 플래그
- API·DB 지연과 재시도 현황
- 승인 대기 사유

운영자 확인은 계산 결과를 임의로 수정하는 권한이 아니라 상태를 승인·보류하는 절차로 제한한다.

## 143. 자동 보정 제한

결측·이상값을 자동 보정할 수 있는 범위는 사전에 정의한다.

- 거래일 순서 정렬과 중복 제거는 허용
- 형식 변환과 명시된 단위 변환은 허용
- 가격·거래량 값을 추정해 채우는 보정은 기본 금지
- 원천 데이터가 없는 봉의 생성은 금지
- 보정된 값은 원본값과 구분해 기록

허용 범위를 벗어난 보정은 자동 실행하지 않고 검토 상태로 보낸다.

## 144. 문서 항목의 구현 추적

각 개선 항목은 문서 번호와 구현·테스트 대상을 연결한다.

```text
문서 항목 ID
→ 구현 모듈/API
→ 테스트 케이스
→ 운영 지표
→ 배포 버전
```

추적 연결이 없는 문서 항목은 원칙 제안으로만 표시하고 운영 보장으로 표현하지 않는다. 반대로 구현된 정책이 문서에 없으면 배포 완료로 처리하지 않는다.

## 154. 통합 분석 개발 진행 상태

현재 구현된 통합 흐름은 다음과 같다.

```text
활성 국내·해외 유니버스
→ DB 저장 일·주·월봉
→ 다중 시간봉 추천 계산
→ OBV·ADL Signal 및 거래량·추세 점수 반영
→ 통합 API 응답
→ kis_cache 저장
→ automation_runs 실행 이력
→ 완료·실패 알림 경로
→ 결과 표·티커 복사·차트 모달
```

검증된 항목:

- 통합 API TypeScript 검사
- 통합 결과 컴포넌트 회귀 검사
- 기술적 진입 분석 핵심 테스트
- 전체 Vitest 테스트 321건

운영 환경에서의 실제 KIS 수집부터 DB 적재, 분석, 알림까지의 종단간 검증은 인증정보와 운영 데이터가 필요한 별도 운영 검증으로 구분한다. 해당 검증 전에는 개발 완료를 운영 완료로 간주하지 않는다.

## 145. 입력 스냅샷 잠금

실행이 시작된 뒤 입력 데이터가 갱신되어도 해당 실행은 최초로 확정한 스냅샷을 계속 사용한다.

- 실행 시작 시 유니버스·봉 범위·정책 버전 잠금
- 수집 완료 시 원천 응답 해시 확정
- 잠금 이후 변경은 다음 실행에만 반영
- 잠금 실패 또는 스냅샷 불완전 시 계산 중단

이를 통해 같은 실행 안에서 종목별로 서로 다른 최신성 기준이 섞이는 문제를 방지한다.

## 146. 점수 설명 가능성

종합점수는 단일 숫자로만 제공하지 않고 점수 구성과 제한 요인을 함께 보여준다.

- 영역별 점수: 가격·모멘텀·추세·수급·거래량·위험
- 영역별 가중치와 적용 여부
- 가산·감산된 지표
- 점수 상한·하한 및 제외 규칙
- 품질 점수와 기술 점수의 분리

점수식이 변경되면 과거 점수와 새 점수를 같은 의미로 비교하지 않으며, 반드시 버전을 표시한다.

## 147. 지표 계산 가능 구간

지표별 최소 필요 봉 수를 명시하고 부족한 경우 임의의 초기값을 사용하지 않는다.

```text
필요 봉 수 확인
→ 충분하면 계산
→ 부족하면 미계산 상태
→ 종합점수에서 정책에 따라 제외 또는 후보 제외
```

초기 EMA 시드와 Bollinger 계산에 사용되는 내부 초기 구간은 최종 신호 봉과 구분한다. 계산 가능 구간이 달라지면 결과 비교 시 해당 차이를 표시한다.

## 148. 데이터 정정 전파

원천 봉이 정정되면 영향을 받는 범위를 추적해 파생 결과를 함께 재검증한다.

- 정정된 일봉 식별
- 영향을 받는 주봉·월봉 식별
- 영향받는 지표·점수·후보 식별
- 승인 결과와 알림 이력 확인
- 필요한 범위만 재계산

정정 전 결과는 감사용으로 보존하고, 정정 후 결과를 새로운 버전으로 생성한다. 영향 범위를 계산하지 못하면 관련 결과를 자동 승인하지 않는다.

## 149. 알림 회수 및 정정 알림

잘못된 데이터로 발송된 알림은 일반 재전송과 구분해 처리한다.

- 원래 알림 ID와 정정 사유 연결
- 회수 가능 채널과 불가능한 채널 구분
- 회수가 불가능하면 정정 알림 발송
- 사용자에게 기존 정보가 정정되었음을 명시
- 정정 알림의 중복 발송 방지

정정 알림은 새로운 매수 신호로 집계하지 않으며, 원래 후보의 상태 이력에 연결한다.

## 150. 스키마 변경 안전성

분석 결과 스키마 변경은 읽기·쓰기 호환 단계를 거친다.

```text
확장 필드 추가
→ 구·신 필드 동시 처리
→ 소비자 전환 확인
→ 구 필드 제거
```

필드 의미 변경이나 단위 변경은 이름을 재사용하지 않고 새 버전 필드 또는 새 계약 버전을 사용한다. 마이그레이션 실패 시 기존 결과 조회가 중단되지 않아야 한다.

## 151. 실행 재개 지점

장시간 작업은 전체 재시작 대신 마지막으로 확정된 단계부터 재개한다.

- 단계별 checkpoint 저장
- checkpoint의 입력 스냅샷·정책 버전 검증
- 이미 확정된 종목은 멱등 재처리
- 손상된 checkpoint는 무시하고 안전한 이전 지점 사용
- 재개 범위와 건너뛴 범위 기록

재개는 성공률을 높이기 위한 기능이지만, 최신성 검증과 중복 방지 검사를 생략할 수 없다.

## 152. 분석 결과의 외부 사용 제한

분석 결과는 투자 판단을 돕는 정보이며 자동 주문이나 확정적 수익 예측으로 해석되지 않도록 사용 범위를 제한한다.

- `APPROVED`는 데이터·정책 검증 완료를 의미할 뿐 수익 보장을 의미하지 않음
- `CAUTION`, `STALE`, `LOW_DATA_CONFIDENCE` 결과는 자동 주문 입력으로 사용하지 않음
- 추천 매수가·목표가·손절가는 계산 근거와 위험 플래그를 함께 표시
- 외부 공유·내보내기에도 기준시각과 데이터 상태 포함

시스템 외부로 결과를 전달할 때도 내부의 상태·최신성·근거 정보를 제거하지 않는다.

## 153. 1차 구현 상태

기존 호출부와의 호환성을 유지하는 범위에서 일봉 골든크로스 계산 결과에 다음 공통 메타데이터를 반영했다.

- 최신·직전 봉의 거래일시
- 최신·직전 봉 데이터의 갱신일시
- 입력 데이터 품질 상태
- 충분한 이력 부족 상태
- 유효하지 않은 입력 포함 여부

구현 위치는 `lib/daily-golden-cross.ts`이며, 기존 결과 계산·캐시 저장 흐름은 유지한다. 관련 단위 테스트와 TypeScript 검사를 통과한 뒤 다음 단계에서 주봉·월봉 및 통합 API 응답에도 동일한 계약을 확장한다.
